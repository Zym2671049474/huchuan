## 二、三段数字的含义

```
v 0 . 2 . 0
  │   │   └── PATCH：向后兼容的问题修正
  │   └────── MINOR：向后兼容的功能新增
  └────────── MAJOR：不兼容的变更
```

| 段 | 什么时候 +1 | 示例 |
|---|---|---|
| **MAJOR** | **不兼容**的变更（协议不兼容、换签名密钥导致不能覆盖安装、配置格式破坏性变更）| 改用全新传输协议 |
| **MINOR** | 向后兼容的**新功能** | 新增剪贴板互传、新增「永久开启」开关 |
| **PATCH** | 向后兼容的**问题修正**（修 bug、改文案、调性能）| 修「点通知打不开文件」|

### 硬规则

1. **任一段 +1，其右侧段必须归零**：`v0.2.3` 出新功能 → `v0.3.0`（不是 `v0.3.3`）。
2. **只在 `git tag` 时定版**，不在提交里随手改。
3. **`versionCode` 必须严格单调递增**（Android 用它判断升级），统一用：
   ```
   versionCode = MAJOR*10000 + MINOR*100 + PATCH
   ```
4. **`versionName` 就是 `X.Y.Z`**（清单里不带 `v` 前缀，如 `0.2.0`）。

### 为什么必须用这个公式（不能省 MAJOR 位）

实测各版本的编码：

| versionName | MAJOR*10000+MINOR*100+PATCH |
|---|---|
| `0.1.0` | 100 |
| `0.2.0` | **200** ← 当前 |
| `0.3.0` | 300 |
| `0.99.99` | 9999 |
| `1.0.0` | 10000 |

看着 `0.x` 阶段可以直接写 `MINOR*100+PATCH`，**但那样会撞车**：

```
简化方案 MINOR*100+PATCH：
  v0.99.99 → 9999
  v0.100.0 → 10000   ← 与下面相等
  v1.0.0   → 10000   ← 冲突！升级判断会错乱
```

所以**从一开始就用完整公式**，不要为了眼下好看而省位。

## 三、`v0.x` 阶段的特殊约定

**`0.x.y` 表示"接口/协议还可能变"**：MAJOR 为 0 时，MINOR 的递增**允许包含不兼容改动**。
本项目当前就在这个阶段。

### 从这里开始对齐

项目历史没有版本号，本次**从当前可用状态起算**：

| 版本 | 对应状态 | 判定依据 |
|---|---|---|
| `v0.1.0` | 首次能与小米 15 完成互传 | 实测收到文件（605252 / 913530 字节）|
| **`v0.2.0`** | **当前**：磁贴开关 + 四状态通知 + 分享卡片 + 点击打开文件 | 19:56 实测收到 918077 字节且通知可打开 |
| `v0.3.0` | 计划：剪贴板/文本互传（M7） | — |

> **为什么不从 `v1.0.0` 起**：1.0 意味着"协议稳定、可给外人用"。
> 现在只有一台发送端（Mi 15）验证过、没有公开发布，定 1.0 会误导使用者。

## 四、版本与里程碑的对应

现有路线图是 **M1–M7**（见 [进度](../03-进度/进度.md)），两者关系：

| 里程碑 | 含义 | 对应版本 |
|---|---|---|
| M1–M5 | 协议基础 / P2P / BLE / 传输（**内部能力**）| 合并进 `v0.1.0` |
| M6 | 双机联调 | `v0.1.0` |
| M7 | 剪贴板/文本互传 | 目标 `v0.3.0` |

**关系原则**：M 是**开发里程碑**（做到哪一步），v 是**交付版本**（能给别人用的东西）。
多个 M 可以合成一个 v；一个 v 也可以只含半个 M。

## 五、什么时候打 tag

**满足全部条件才打 tag**：

1. `./build.sh` 退出码 **0**，`./tests/run.sh` **全绿**；
2. 关键功能有**实测证据**（不是"应该能行"）；
3. `docs/03-进度/进度.md` 已更新到该版本状态；
4. APK 能**覆盖安装**（签名一致）。

```sh
# 打 tag（tag 也要推送到 GitHub）
git -c safe.directory='*' tag -a v0.2.0 -m "v0.2.0: 磁贴开关 + 四状态通知 + 点击打开文件"
git -c safe.directory='*' push origin v0.2.0    # ← 会被墙，改用 API 建 tag
```

> ⚠️ `github.com:443` 被墙，tag 推送同样要走 API，见 [推送指南](../04-参考/推送指南.md)。

## 六、Android 清单里的写法

```xml
<manifest ...>
    <uses-permission .../>
    <application ...>
        <!-- versionCode 单调递增；versionName 不带 v 前缀 -->
    </application>
</manifest>
```

> 本项目 `AndroidManifest.xml` **目前尚未声明 `versionCode`/`versionName`**
> （构建脚本用的是 `--min-sdk-version` / `--target-sdk-version`）。
> 首次对外发布前需要补上，并同步到本文件的「当前版本」表。

---

## 七、提交信息里要不要带版本

- **平时提交不带版本号**，只带踩坑编号：`fix: 修通知点击（P122）`
- **发布提交带头**：`release: v0.2.0 —— 端到端互传可用`
- **不要在每次提交里改版本号** —— 版本是"发布"这个动作的产物，不是开发节奏。
