## [P001] MAC 地址是死字段，root/Shizuku 完全不需要
- **发现时间**：2026-10-15
- **现象**：CatShare 原版显示"Root 不可用"仍能正常互传；作者为此引入了 Shizuku + root 双路径共 140 行代码
- **根因**：协议里 `P2pInfo.mac` 字段**写了但从不读**。
  - 发送端 `P2pSenderService.kt:432` `mac = cipher?.encrypt(p2pMac)` —— 加密后发出去
  - 接收端 `GattServerService.kt:168` `mac = cipher.decrypt(p2pInfo.mac)` —— 解密后赋给 p2pInfo
  - `P2pReceiverService` 建连只用 `ssid`/`psk`/`port`，**`p2pInfo.mac` 引用数 = 0**
- **证据**：全库 `rg -n "\.mac\b" app/src/main/java/` → 仅 1 处命中（就是上面那个解密赋值）
- **解法**：新项目**彻底不实现 MAC 获取**，删掉 Shizuku/root 依赖
- **收益**：省掉 ~200 行代码 + 一个 20 秒超时的 Service 绑定流程

## [P003] aapt2 用 $HOME/android.jar 报 "attribute not found"
- **现象**：
  ```
  AndroidManifest.xml:3: error: attribute android:minSdkVersion not found.
  ```
  且输出 base.apk 为 **0 字节**
- **根因**：`$HOME/android.jar` 是 **javac 用的 classpath jar，不含资源表**；aapt2 需要用真实 framework
- **解法**：`aapt2 link -I /system/framework/framework-res.apk`
- **记忆点**：
  - `javac -cp` → `$HOME/android.jar`
  - `aapt2 link -I` → `/system/framework/framework-res.apk`
  - **两者不能混用**

## [P004] d8 报 "Invalid output: out/dex"
- **现象**：`Error: Invalid output: out/dex / Output must be a .zip or .jar archive or an existing directory`
- **根因**：d8 **不会自动创建**输出目录（与 javac 的 `-d` 不同）

## [P005] 签名/重打包时 resources.arsc 和 .so 必须 Stored
- **现象**：`INSTALL_FAILED_INVALID_APK: Failed to extract native libraries, res=-2`
  和 `... resources.arsc ... stored uncompressed and aligned on a 4-byte boundary`
- **根因**：`targetSdk >= 30` 且 `extractNativeLibs=false` 时，系统要求特定条目**不得压缩**
- **解法**：打包时用 `zip -0`（Stored）处理 `resources.arsc` 与 `lib/**/*.so`，再 `zipalign -f 4`
- **注**：本项目 MVP 不含 .so，但仍需保证 resources.arsc 为 Stored

## [P006] smali 手写代码极易踩寄存器坑
- **现象**：`java.lang.VerifyError: ... onCreate ... 'this' argument 'Reference: java.lang.String' not instance of 'Reference: moe.reimu.catshare.MainActivity'`
- **根因**：在 `.registers 2` 的方法里用 `v0` 当临时寄存器，**覆盖了后续要当 `this` 用的寄存器**
- **解法**：`.registers 3` + 专用 scratch 寄存器；**更根本的解法是不要手写 smali**
- **结论**：新项目用 Java 源码 → javac → d8，彻底避开此坑

## [P010] build.sh 静默失败：javac 报错仍产出"成功"的 APK
- **现象**：javac 编译失败（1 error），但 build.sh 继续走完 6 步并报告"✅ 构建完成"，产出 12873 字节的 APK
- **根因**：`javac ... 2>&1 | grep -v "^Note:" || true` —— **管道会把 javac 的退出码换成 grep 的**，
  加上 `|| true`，`set -e` 永远不会触发
- **解法**：改为 `if ! javac ... >"$OUT/javac.log" 2>&1; then 打印并 exit 1; fi`
- **教训**：**任何 `cmd | grep` 都会吞掉 cmd 的退出码**。构建脚本里判断成败必须用 `if !` 或 `PIPESTATUS`

## [P012] KeyAgreement.generateSecret(String) 编译桩与运行时返回类型不一致
- **现象**：`error: incompatible types: SecretKey cannot be converted to byte[]`
- **根因**：Android 的 `android.jar` 桩里 `generateSecret(String)` 返回 `SecretKey`，
  但**运行时 Conscrypt 实际返回 `byte[]`**
- **解法**：用 `Object` 接收后 `instanceof` 分支
  ```java
  Object secret = ka.generateSecret("TlsPremasterSecret");
  byte[] keyBytes = (secret instanceof byte[]) ? (byte[]) secret
                  : ((javax.crypto.SecretKey) secret).getEncoded();
  ```
- **验证**：真机 T3 加密自检通过 → 运行时确实走 `byte[]` 分支

## [P014] github.com:443 被墙，但 api.github.com 可达 → git push 永久卡住
- **现象**：
  - `curl https://api.github.com/...` ✅ 正常（能建仓库、能查 API）
  - `git push https://github.com/...` ❌ `Failed to connect to github.com:443 after 31592 ms`
  - 第一次尝试用 credential helper 时**无输出卡死 60 秒以上**
- **根因**：
  1. **`github.com:443` 与 `codeload.github.com` 在本网络不可达**，而 `api.github.com` 走的是不同 IP/链路，可达
  2. credential helper 里引用了**未 export 的 `$GH_TOKEN`**，git 拿到空密码后静默等待输入
- **可达性实测**：
  | 端点 | 状态 |
  |---|---|
  | `api.github.com:443` | ✅ |
  | `github.com:443` | ❌ |
  | `codeload.github.com` | ❌ |
  | `ssh.github.com:443` | ✅ |
  | `github.com:22` | ✅ |
- **解法（本项目采用）**：改用 **Git Data API 推送**，全程只走 `api.github.com`
  ```sh
  GH_TOKEN=xxx GH_REPO=owner/name node scripts/api-push.mjs
  ```
  流程：`POST /git/blobs`（逐文件 base64）→ `POST /git/trees` → `POST /git/commits` → `PATCH /git/refs/heads/main`
- **备选**：SSH over 443（`ssh.github.com:443` 可达），需先把公钥注册到 GitHub 账号

### 连带踩的坑
- **空仓库无法建 blob**：`POST /git/blobs` → `409 Git Repository is empty`。
  必须先用 **contents API** 建一个占位文件（如 `.gitkeep`）让仓库非空：
  ```sh
  curl -X PUT "$API/contents/.gitkeep" -d '{"message":"init","content":"","branch":"main"}'
  ```
- **ref 已存在**：`POST /git/refs` → `422 Reference already exists`。应先 `PATCH /git/refs/heads/main`
- **中文文件名被八进制转义**：`git ls-files` 输出 `"docs/\345\215\217..."` 导致 `ENOENT`。
  必须加 `-c core.quotepath=false`：
  ```js
  execFileSync('git', ['-c','core.quotepath=false','ls-files'])
  ```

## [P016] P2P 建组："第一个" CONNECTION_CHANGED 广播是中间态，会提前放行
- **现象**：`createGroup` 返回成功，但 `getSession()` 为 `null`，日志显示"会话信息尚未就绪"
- **根因**：`WIFI_P2P_CONNECTION_CHANGED_ACTION` **会来两次**：
  ```
  16:16:05.134  groupFormed=false  group=null          ← 中间态（组还没真正建好）
  16:16:05.167  createGroup 的 ActionListener 回调成功
  16:16:05.497  groupFormed=true   group=DIRECT-xxx    ← 真正的组信息（晚 330ms）
  ```
  用 `CountDownLatch` 等"第一个"广播 → 被 `groupFormed=false` 提前放行
- **解法**：不要等"广播到达"，要等"**状态就绪**"：
  ```java
  private void awaitGroupReady(int timeoutSec) {
      long deadline = System.currentTimeMillis() + timeoutSec * 1000L;
      while (System.currentTimeMillis() < deadline) {
          if (lastSession != null) return;   // group 非空才算就绪
          Thread.sleep(100);
      }
  }
  ```
- **教训**：Android 的 `*_CHANGED` 类广播常伴随**中间态**（值还是旧的/空的）。
  判断就绪要看**内容**，不要看**次数**

## [P018] BLE 特征值读写必须支持分块（默认 MTU 只有 23 字节）
- **现象**：`DeviceInfo`（含 124 字节 Base64 公钥）远超默认 ATT MTU，一次读不完
- **根因**：BLE 默认 ATT MTU = 23 字节，净荷仅 **20 字节**。
  读写长属性时系统会按 offset 多次请求
- **解法**（两层都要处理）：
  ```java
  // 服务端：按 offset 切片返回，用 GATT_INVALID_OFFSET(0x07) 拒绝越界
  byte[] piece = Arrays.copyOfRange(snapshot, offset, snapshot.length);
  server.sendResponse(device, requestId, 0, 0, piece);

  // 服务端：累积分块写入（preparedWrite=true 时继续等）
  System.arraycopy(value, 0, buf.data, offset, value.length);
  if (preparedWrite) return;          // 还有后续分片
  byte[] full = Arrays.copyOfRange(buf.data, 0, buf.length);

  // 客户端：协商 MTU 后再传，onCharacteristicWrite 驱动下一片
  g.requestMtu(517);
  // onMtuChanged → writeChunkSize = mtu - 3
  ```
- **注意**：`onDescriptorWriteRequest` **必须回 sendResponse**，否则对端订阅时超时

## [P021] ★致命★ 缺 `INTERNET` 权限 → 所有 socket 操作 EPERM
- **现象**：BLE 发现、GATT 读写、ECDH 解密、WiFi Direct 加入组**全部成功**，
  一到建 socket 就挂：
  ```
  ❌ java.net.SocketException: socket failed: EPERM (Operation not permitted)
  ```
  这个报错极具误导性 —— 看起来像 SELinux 或 root 问题，其实是**权限没声明**
- **根因**：`AndroidManifest.xml` 里**没有** `<uses-permission android:name="android.permission.INTERNET" />`。
  Android 上**任何** socket（包括 `127.0.0.1` 回环、`ServerSocket` 监听）都需要 INTERNET 权限；
  没有它就返回 `EPERM`
- **为什么没早发现**：M1/M2 只测到 BLE 和 WiFi Direct，**从没真正开过 socket**。
  M3/M4 引入 HTTP 服务 + WS 连接后第一次碰 socket，才暴露
- **解法**：
  ```xml
  <uses-permission android:name="android.permission.INTERNET" />
  ```
- **验证方法**（已内置为自检）：
  ```java
  // net/SocketSelfTest.java —— 起回环 ServerSocket+Socket，返回 null 表示正常
  ```
  真机日志：`HuChuan.SocketTest: socket 自检通过: ok`
- **教训**：
  1. **`EPERM` on socket ⇒ 先查 INTERNET 权限**，不要往 SELinux/root 方向查
  2. 每个新引入的系统能力（这里是网络）都要**立刻做自检**，别等联调
  3. manifest 权限清单要跟代码用到的 API **逐项对照**一遍

## [P022] 小米原生互传的 P2pInfo 比 CatShare 多 5 个字段
- **现象**：小米 15 通过 BLE 写来的 JSON 含 `freq` / `G` / `M` / `P` / `transfer_mode`，
  而 CatShare 的 `P2pInfo` **完全没有**这些字段
  ```json
  {"id":"7d1a","mac":"...","port":57832,"freq":2412,"G":1,"M":1,"P":2,
   "ssid":"...","psk":"...","key":"MFkw...","transfer_mode":0}
  ```
- **含义**：说明对面跑的是**小米原生互传联盟协议**，是 CatShare 实现的**超集**
  （`freq`=频段MHz 2412/5745；`G`/`M`/`P` 疑似 GO capability/mode/preference）
- **处理**：`P2pInfo` 增加这 5 个字段，**解析时容忍缺失**（`optInt(...,0)`），
  发送时按需带上 `freq` / `transfer_mode`
- **启示**：**互传联盟协议 ≠ CatShare**。CatShare 只是其中一个实现，
  真机联调要以**小米实际发来的报文**为准

## [P023] ★致命★ 传输层必须是 TLS（HTTPS/WSS），不是明文 HTTP
- **现象**：真机联调时对方在"已加入组"之后就不再请求；我们起的是明文 HTTP 服务
- **根因**：CatShare 发送方用 Ktor **`sslConnector` + 自签名证书**：
  ```kotlin
  val keyStore = buildKeyStore { certificate("sampleAlias") { ... } }
  sslConnector(keyStore, keyAlias="sampleAlias", ...) { port = 0 }
  ```
  与之对应，接收方：
  ```kotlin
  sslSocketFactory(sslContext.socketFactory, FakeTrustManager())
  hostnameVerifier { _, _ -> true }
  ```
  即：**传输层是 TLS，但证书内容不被校验**。小米原生互传同样走 https/wss。
- **解法**：发送方必须提供 TLS
  ```java
  // 服务端：用随包分发的自签名证书
  SSLContext sctx = Tls.serverContext(ctx);          // 加载 res/raw/huchuan.p12
  transfer.startHttpServer(true, sctx);              // HTTPS
  transfer.startWsServer(wsPort, sctx);              // WSS

  // 客户端：信任一切 + 放行主机名
  SSLContext cctx = Tls.clientContext();
  ```
- **证书来源**：Android **没有公开的 X.509 证书生成 API**，所以证书是构建期用
  `keytool -genkeypair -keyalg EC -groupname secp256r1` 生成后放进 `res/raw/`。
  它对端本来就不校验，内容无所谓，**关键是有 TLS 握手**
- **验证**：JVM 端到端测试 —— TLS 握手成功（`TLS_AES_256_GCM_SHA384`）→ HTTPS 200 →
  2MB 字节级一致

## [P024] /download 返回的是 **ZIP 流**，不是裸文件
- **现象**：即使走通 HTTPS，按裸字节收下来的文件对方也解不开
- **根因**：CatShare 的 `/download` 用 `ZipOutputStream` 打包：
  ```kotlin
  call.respondOutputStream(ContentType.Application.Zip, HttpStatusCode.OK) {
      ZipOutputStream(this).use { zo ->
          zo.putNextEntry(ZipEntry("$i/${rf.name}"))    // 条目名 = "序号/文件名"
  ```
  接收方用 `ZipInputStream` 解开（`saveArchive`）
- **解法**：发送端 `ZipOutputStream` 打包，条目名 `"0/" + 文件名`；
  接收端 `ZipInputStream` 解包并取条目名最后一段
- **注意**：ZIP 长度事先未知，HTTP 头用 **`Transfer-Encoding: chunked`**
  （不能给 `Content-Length`）

## [P025] WS 端点路径是 `/websocket`，不是 `/`
- **证据**：`val wsSession = client.webSocketSession("wss://${hostPort}/websocket")`
- **解法**：服务端 `startServer(port, "/websocket", ...)`，客户端 `connect(host, port, "/websocket", ...)`
- **教训**：三个端点要素都要对齐 —— **协议(scheme) + 路径(path) + 端口(port)**，
  少一个都连不上，且报错往往不指向真正原因

## [P026] ★致命★ status 必须在收到 sendRequest 后**立刻**回，对端只等 10 秒
- **现象**（真机日志）：
  ```
  17:09:15.478  ← action:0:versionNegotiation?{"versions":[1],"version":1}
  17:09:15.478  → ack versionNegotiation          ← 我们回了
  17:09:25.259  连接关闭                            ← 恰好在 +10s
  17:09:25.408  P2pStateMachine.handleGroupRemoved  ← 对方撤了组
  ```
  TLS/WSS/版本协商**全部成功**，然后就静默断开
- **根因**：CatShare 接收方等用户确认用的是
  ```kotlin
  val userResponse = withTimeoutOrNull(10000L) { waitForAction(localTaskId) }
  if (userResponse != true) { sendStatus(99, taskId, 3, "user refuse"); throw CancelledByUserException() }
  ```
  **10 秒是对方的确认窗口**。超时即视为拒绝并 `removeGroup` 断开。
  我们虽然回了 status，但**晚于对方的等待窗口**（或 id/时序不匹配），于是被判超时
- **解法**：收到 `sendRequest` 后**立即**回 status，再去下载
  ```java
  JSONObject req = recv.awaitSendRequest(20);
  recv.respond(taskId, 99, 1, "ok");    // ★ id=99，与 CatShare sendStatusIgnoreException(99,...) 一致
  recv.download(...);                    // ★ 紧接着就下载
  ```
- **另一个隐含约束**：发送方的 `transferStartFuture` 等的是**接收方真的发起 /download**，
  超时 30 秒（`awaitWithTimeout(30s, "Waiting for start transfer")`）。
  所以 **status 和 download 之间不能有任何耗时操作**
- **验证**：写了 CatShare 发送方时序的完整模拟（TLS + /websocket + status(99) + HTTPS ZIP），
  1MB 字节级一致

## [P031] LD_LIBRARY_PATH 在扩展工具间的冲突（反复踩）

- **通用规避**：用 `python3` 的 `zipfile`/`tarfile` 替代 `unzip`/`zip`，
  减少一个依赖

## [P036] ★ 手写 smali 的寄存器类型冲突 —— 同一个 VerifyError 犯了两次
- **现象**：
  ```

  register v4 has type Reference: java.lang.String but expected Integer
  ```
- **直接原因**：我在一个方法里把同一寄存器先后当不同类型用：
  ```smali
  const-string v4, "taskId"          # v4 = String
  const-high16 v5, 0x4000000         # v5 = int
  ...
  invoke-static {..., v6, v5}        # v5 又当 int 传给 getBroadcast
  move-result-object v5              # v5 变成 PendingIntent
  sget v6, R$drawable;->ic_downloading:I   # v6 从 Intent 变成 int
  move-result-object v6              # v6 又变成 Builder
  ```
- **根本原因**：**smali 汇编器不做寄存器类型检查，ART 的验证器才做。**
  所以"编译通过"完全不代表"能跑"。
- **最阴险的一次**：以为某个寄存器"已经没用了"就可以复用，但它在**后面**还被引用：
  ```smali
  # v0 在 456 行还是 Intent
  invoke-static {p0, p1, v0, p6}, Landroid/app/PendingIntent;->getBroadcast(...)
  # 我在 472 行把 v0 当 String 用 → 冲突
  move-object v0, p2
  ```
  **判断寄存器是否可复用，必须看它在整个方法里的完整生命周期，不能只看插入点附近。**
- **正确做法（按推荐顺序）**：
  1. **能用 Java 就用 Java** —— `javac` + `d8`，编译器保证类型正确（P028 的教训）
  2. 必须手写 smali 时：
     - **一个寄存器只装一种类型**，绝不复用
     - 需要临时寄存器就**先把 `.registers` 调大**（如 11 → 14），用全新的 `vN`
     - **改完必须用 `d8` 复验**：
       ```sh
       java -cp $D8_JAR com.android.tools.r8.D8 --output /tmp/out --lib $HOME/android.jar new.dex
       # 无输出 = 通过；报错就是真有问题
       ```
       `d8` 用的是同一套校验规则，能在安装前抓住这类错误。
- **教训**：
  - `smali` 汇编成功 ≠ 字节码合法
  - **每次改完 smali，必须跑一遍 d8 校验再打包**（当时我跳过了这步，直接装机 → 崩）
  - 崩溃出现在"真实传输时"而不是启动时，因为 ART 是**懒验证**（用到才验证），
    所以启动测试通过也说明不了问题

## [P038] ★★★ 手写 smali 的致命陷阱：`.registers` 决定 pX 映射，改它 = 全盘洗牌
- **连续两次崩溃的真正根因**（P036 的诊断是错的，特此更正）
- **smali 寄存器映射规则**（必须背下来）：
  ```
  .registers N，方法有 K 个参数（含 this）
  → 参数寄存器 p0..p(K-1) 占据 v(N-K) .. v(N-1)
  → 纯局部寄存器只有 v0 .. v(N-K-1)
  ```
- **我犯的错**：原方法 `.registers 11`（9 个参数 → p0=v2，局部只有 v0,v1）。
  我为了"腾出临时寄存器"把它改成 `.registers 14`，
  结果 p0 从 v2 变成 v5 —— **所有 pX 的物理寄存器全部平移**。
  原始代码里针对 v2/v7 等具体编号成立的类型关系被打乱 → VerifyError。
- **第二次更蠢**：`.registers 17`，9 个参数 → p0=v8。
  我用了 v8,v9,v10,v11,v12 当"局部寄存器"，
  **它们其实全都是参数寄存器**（v8=p0 Context，v9=p1 taskId…）。
  把 taskId(int) 当 PendingIntent 用 → ART 报
  `register v9 has type Reference: PendingIntent but expected Integer`
- **正确做法**：
  1. **先算清楚**：局部区 = `v0 .. v(N-K-1)`，只用这个区间内的寄存器
  2. 需要更多局部寄存器 → **调大 `.registers`，同时重新计算 pX 起点**
     （不要以为"原来的 pX 还在原地"）
  3. **最稳妥**：`.registers` 设得足够大（如 20），
     让局部区（v0..v10）与参数区（v11..v19）完全分离，绝不重叠
- **为什么 d8 校验骗了我**：d8 的输入是 dex 时，它只做自己的 IR 转换，
  **不运行 Android 的 verifier**。"d8 无输出"是假阳性，不能作为验证依据。

## [P044] ★★★ 用 kotlinc 编译的类直接替换进 APK 会崩 —— R8 已删除大量 API
**结论：不要用 kotlinc 编译整包替换。** 这个 APK 被 R8 激进压缩过，
编译期依赖库里的 API 与运行时 APK 里的**不是同一套**。

### 实测到的三类不兼容（全都会导致运行时崩溃）

**1) 静态工厂方法被删**
```
NoSuchMethodError: No method NotificationManagerCompat.from(Context)
```
编译期 androidx 里有 `from()`；运行时 APK 里 `NotificationManagerCompat`
**只剩 3 个成员**：`<init>(Context)`、`notify(int,Notification)`、字段 `mNotificationManager`。
原版源码里的 `from(ctx)` 被 R8 内联成了 `new NotificationManagerCompat(ctx)`。

**2) 构建器/DSL 函数被删**
```
NoSuchMethodError: No virtual method Json.getSerializersModule()
```
编译期 `Json.serializersModule` 是 **private 字段 + public getter**；
运行时 APK 里是 **public 字段、无 getter**。方向正好相反。
`JsonKt`（即 `Json { }` DSL）、`JsonBuilder.setIgnoreUnknownKeys` 运行时全都不存在。

**3) API 被内联成字段直写**
```smali
# 原版（R8 优化后）
iput-object p2, p5, Landroidx/core/app/NotificationCompat$Builder;->mContentTitle:Ljava/lang/CharSequence;
# 而不是
invoke-virtual {p5, p2}, ...->setContentTitle(...)
```
运行时 `NotificationCompat$Builder` 只剩：
`<init> / addAction / build / limitCharSequenceLength / setFlag / setStyle`
—— `setContentTitle`、`setLargeIcon`、`setDeleteIntent` 全被删了，只能写字段。

### 怎么判断哪些 API 还能用（可复用脚本）
不要靠 `strings`/子串搜索（dex 的字符串池与方法表是分开的，会误判）。
**直接解析 dex 的方法表**：
```python
# dex 头偏移：string_ids(56) type_ids(64) proto(72) field(80) method(88) class_def(96)
sid_n, sid_o = struct.unpack_from('<II', d, 56)
tid_n, tid_o = struct.unpack_from('<II', d, 64)
mid_n, mid_o = struct.unpack_from('<II', d, 88)
# method_id_item = (class_idx:H, proto_idx:H, name_idx:I)
```
拿到 `Lcls;->name` 全集后，逐个核对**我们编译产物引用的每个方法**。
注意要沿着 `class_def.superclass_idx` 向上找（继承方法不在子类自己的表里）。
脚本：`$HOME/kotlin-build/verify3.py`

### ✅ 正确做法：只改方法体，别整类替换
最终可行的方案（本机验证 0 崩溃）：
1. 用 baksmali 反编译**原始 APK**，作为基底（`/tmp/orig2/smali`）
2. 找到要改的方法，**照抄它的风格**（R8 内联后的写法）
3. 只替换**这一个方法**，其余 89 个类全部还原成原版
4. 结果：整个 APK **只有 1 个文件与原版不同**

### 关键坑：`.registers` 与参数寄存器
原版方法 `.registers 11` + 9 个参数 → 只有 `v0`、`v1` 是可自由使用的局部寄存器，
`v2..v10` 全是参数寄存器。**改 `.registers` 会整体平移 `pX` 的映射**，
必须同步改所有 `pX` 引用（详见 P038）。
