## [P001] MAC 地址是死字段，root/Shizuku 完全不需要
- **发现时间**：2026-10-15
- **现象**：CatShare 原版显示"Root 不可用"仍能正常互传；作者为此引入了 Shizuku + root 双路径共 140 行代码
- **根因**：协议里 `P2pInfo.mac` 字段**写了但从不读**。
  - 发送端 `P2pSenderService.kt:432` `mac = cipher?.encrypt(p2pMac)` —— 加密后发出去
  - 接收端 `GattServerService.kt:168` `mac = cipher.decrypt(p2pInfo.mac)` —— 解密后赋给 p2pInfo
  - `P2pReceiverService` 建连只用 `ssid`/`psk`/`port`，**`p2pInfo.mac` 引用数 = 0**
- **证据**：全库 `rg -n "\.mac\b" app/src/main/java/` → 仅 1 处命中（就是上面那个解密赋值）
- **解法**：新项目**彻底不实现 MAC 获取**，删掉 Shizuku/root 依赖
- **收益**：省掉 ~200 行代码 + 一个 20 秒超时的 Service 绑定流程

## [P002] 设备上无法用 Kotlin / Gradle
- **现象**：想直接 fork CatShare（Kotlin + Compose + Gradle 9.2.1）
- **根因**：

  - 无 Android SDK `platforms/`、`build-tools/`
  - `ANDROID_HOME` / `ANDROID_SDK_ROOT` 环境变量值损坏（内容为 `国考2027职位表`）

- **代价**：不能用 Compose → 用原生 View / 纯代码构建 UI，反而体积更小

## [P003] aapt2 用 $HOME/android.jar 报 "attribute not found"
- **现象**：
  ```
  AndroidManifest.xml:3: error: attribute android:minSdkVersion not found.
  ```
  且输出 base.apk 为 **0 字节**
- **根因**：`$HOME/android.jar` 是 **javac 用的 classpath jar，不含资源表**；aapt2 需要用真实 framework
- **解法**：`aapt2 link -I /system/framework/framework-res.apk`
- **记忆点**：
  - `javac -cp` → `$HOME/android.jar`
  - `aapt2 link -I` → `/system/framework/framework-res.apk`
  - **两者不能混用**

## [P004] d8 报 "Invalid output: out/dex"
- **现象**：`Error: Invalid output: out/dex / Output must be a .zip or .jar archive or an existing directory`
- **根因**：d8 **不会自动创建**输出目录（与 javac 的 `-d` 不同）
- **解法**：`mkdir -p out/dex` 后再调用 d8

## [P005] 签名/重打包时 resources.arsc 和 .so 必须 Stored
- **现象**：`INSTALL_FAILED_INVALID_APK: Failed to extract native libraries, res=-2`
  和 `... resources.arsc ... stored uncompressed and aligned on a 4-byte boundary`
- **根因**：`targetSdk >= 30` 且 `extractNativeLibs=false` 时，系统要求特定条目**不得压缩**
- **解法**：打包时用 `zip -0`（Stored）处理 `resources.arsc` 与 `lib/**/*.so`，再 `zipalign -f 4`
- **注**：本项目 MVP 不含 .so，但仍需保证 resources.arsc 为 Stored

## [P006] smali 手写代码极易踩寄存器坑
- **现象**：`java.lang.VerifyError: ... onCreate ... 'this' argument 'Reference: java.lang.String' not instance of 'Reference: moe.reimu.catshare.MainActivity'`
- **根因**：在 `.registers 2` 的方法里用 `v0` 当临时寄存器，**覆盖了后续要当 `this` 用的寄存器**
- **解法**：`.registers 3` + 专用 scratch 寄存器；**更根本的解法是不要手写 smali**
- **结论**：新项目用 Java 源码 → javac → d8，彻底避开此坑

## [P007] 每次卸载重装会改变 app uid，导致 KernelSU 授权失效

## [P010] build.sh 静默失败：javac 报错仍产出"成功"的 APK
- **现象**：javac 编译失败（1 error），但 build.sh 继续走完 6 步并报告"✅ 构建完成"，产出 12873 字节的 APK
- **根因**：`javac ... 2>&1 | grep -v "^Note:" || true` —— **管道会把 javac 的退出码换成 grep 的**，
  加上 `|| true`，`set -e` 永远不会触发
- **解法**：改为 `if ! javac ... >"$OUT/javac.log" 2>&1; then 打印并 exit 1; fi`
- **教训**：**任何 `cmd | grep` 都会吞掉 cmd 的退出码**。构建脚本里判断成败必须用 `if !` 或 `PIPESTATUS`

## [P011] 严格 android.jar 引导类路径下不能用 lambda / 方法引用
- **现象**：
  ```
  error: cannot find symbol
    symbol:   method metafactory(Lookup,String,MethodType,MethodType,MethodHandle,MethodType)
    location: interface LambdaMetafactory
  Fatal Error: Unable to find method metafactory
  ```
- **根因**：`-bootclasspath $HOME/android.jar` 是 Android 的 API 桩，**不含 `java.lang.invoke.LambdaMetafactory`**；
  lambda 与 `::` 方法引用需要它做脱糖
- **解法**：改用**匿名内部类** `new Runnable(){ public void run(){...} }`
- **注意**：不影响 APK 的 `-source 8` 目标，只是编译期限制

## [P012] KeyAgreement.generateSecret(String) 编译桩与运行时返回类型不一致
- **现象**：`error: incompatible types: SecretKey cannot be converted to byte[]`
- **根因**：Android 的 `android.jar` 桩里 `generateSecret(String)` 返回 `SecretKey`，
  但**运行时 Conscrypt 实际返回 `byte[]`**
- **解法**：用 `Object` 接收后 `instanceof` 分支
  ```java
  Object secret = ka.generateSecret("TlsPremasterSecret");
  byte[] keyBytes = (secret instanceof byte[]) ? (byte[]) secret
                  : ((javax.crypto.SecretKey) secret).getEncoded();
  ```
- **验证**：真机 T3 加密自检通过 → 运行时确实走 `byte[]` 分支

## [P014] github.com:443 被墙，但 api.github.com 可达 → git push 永久卡住
- **现象**：
  - `curl https://api.github.com/...` ✅ 正常（能建仓库、能查 API）
  - `git push https://github.com/...` ❌ `Failed to connect to github.com:443 after 31592 ms`
  - 第一次尝试用 credential helper 时**无输出卡死 60 秒以上**
- **根因**：
  1. **`github.com:443` 与 `codeload.github.com` 在本网络不可达**，而 `api.github.com` 走的是不同 IP/链路，可达
  2. credential helper 里引用了**未 export 的 `$GH_TOKEN`**，git 拿到空密码后静默等待输入
- **可达性实测**：
  | 端点 | 状态 |
  |---|---|
  | `api.github.com:443` | ✅ |
  | `github.com:443` | ❌ |
  | `codeload.github.com` | ❌ |
  | `ssh.github.com:443` | ✅ |
  | `github.com:22` | ✅ |
- **解法（本项目采用）**：改用 **Git Data API 推送**，全程只走 `api.github.com`
  ```sh
  GH_TOKEN=xxx GH_REPO=owner/name node scripts/api-push.mjs
  ```
  流程：`POST /git/blobs`（逐文件 base64）→ `POST /git/trees` → `POST /git/commits` → `PATCH /git/refs/heads/main`
- **备选**：SSH over 443（`ssh.github.com:443` 可达），需先把公钥注册到 GitHub 账号

### 连带踩的坑
- **空仓库无法建 blob**：`POST /git/blobs` → `409 Git Repository is empty`。
  必须先用 **contents API** 建一个占位文件（如 `.gitkeep`）让仓库非空：
  ```sh
  curl -X PUT "$API/contents/.gitkeep" -d '{"message":"init","content":"","branch":"main"}'
  ```
- **ref 已存在**：`POST /git/refs` → `422 Reference already exists`。应先 `PATCH /git/refs/heads/main`
- **中文文件名被八进制转义**：`git ls-files` 输出 `"docs/\345\215\217..."` 导致 `ENOENT`。
  必须加 `-c core.quotepath=false`：
  ```js
  execFileSync('git', ['-c','core.quotepath=false','ls-files'])
  ```

## [P016] P2P 建组："第一个" CONNECTION_CHANGED 广播是中间态，会提前放行
- **现象**：`createGroup` 返回成功，但 `getSession()` 为 `null`，日志显示"会话信息尚未就绪"
- **根因**：`WIFI_P2P_CONNECTION_CHANGED_ACTION` **会来两次**：
  ```
  16:16:05.134  groupFormed=false  group=null          ← 中间态（组还没真正建好）
  16:16:05.167  createGroup 的 ActionListener 回调成功
  16:16:05.497  groupFormed=true   group=DIRECT-xxx    ← 真正的组信息（晚 330ms）
  ```
  用 `CountDownLatch` 等"第一个"广播 → 被 `groupFormed=false` 提前放行
- **解法**：不要等"广播到达"，要等"**状态就绪**"：
  ```java
  private void awaitGroupReady(int timeoutSec) {
      long deadline = System.currentTimeMillis() + timeoutSec * 1000L;
      while (System.currentTimeMillis() < deadline) {
          if (lastSession != null) return;   // group 非空才算就绪
          Thread.sleep(100);
      }
  }
  ```
- **教训**：Android 的 `*_CHANGED` 类广播常伴随**中间态**（值还是旧的/空的）。
  判断就绪要看**内容**，不要看**次数**

## [P018] BLE 特征值读写必须支持分块（默认 MTU 只有 23 字节）
- **现象**：`DeviceInfo`（含 124 字节 Base64 公钥）远超默认 ATT MTU，一次读不完
- **根因**：BLE 默认 ATT MTU = 23 字节，净荷仅 **20 字节**。
  读写长属性时系统会按 offset 多次请求
- **解法**（两层都要处理）：
  ```java
  // 服务端：按 offset 切片返回，用 GATT_INVALID_OFFSET(0x07) 拒绝越界
  byte[] piece = Arrays.copyOfRange(snapshot, offset, snapshot.length);
  server.sendResponse(device, requestId, 0, 0, piece);

  // 服务端：累积分块写入（preparedWrite=true 时继续等）
  System.arraycopy(value, 0, buf.data, offset, value.length);
  if (preparedWrite) return;          // 还有后续分片
  byte[] full = Arrays.copyOfRange(buf.data, 0, buf.length);

  // 客户端：协商 MTU 后再传，onCharacteristicWrite 驱动下一片
  g.requestMtu(517);
  // onMtuChanged → writeChunkSize = mtu - 3
  ```
- **注意**：`onDescriptorWriteRequest` **必须回 sendResponse**，否则对端订阅时超时

## [P021] ★致命★ 缺 `INTERNET` 权限 → 所有 socket 操作 EPERM
- **现象**：BLE 发现、GATT 读写、ECDH 解密、WiFi Direct 加入组**全部成功**，
  一到建 socket 就挂：
  ```
  ❌ java.net.SocketException: socket failed: EPERM (Operation not permitted)
  ```
  这个报错极具误导性 —— 看起来像 SELinux 或 root 问题，其实是**权限没声明**
- **根因**：`AndroidManifest.xml` 里**没有** `<uses-permission android:name="android.permission.INTERNET" />`。
  Android 上**任何** socket（包括 `127.0.0.1` 回环、`ServerSocket` 监听）都需要 INTERNET 权限；
  没有它就返回 `EPERM`
- **为什么没早发现**：M1/M2 只测到 BLE 和 WiFi Direct，**从没真正开过 socket**。
  M3/M4 引入 HTTP 服务 + WS 连接后第一次碰 socket，才暴露
- **解法**：
  ```xml
  <uses-permission android:name="android.permission.INTERNET" />
  ```
- **验证方法**（已内置为自检）：
  ```java
  // net/SocketSelfTest.java —— 起回环 ServerSocket+Socket，返回 null 表示正常
  ```
  真机日志：`HuChuan.SocketTest: socket 自检通过: ok`
- **教训**：
  1. **`EPERM` on socket ⇒ 先查 INTERNET 权限**，不要往 SELinux/root 方向查
  2. 每个新引入的系统能力（这里是网络）都要**立刻做自检**，别等联调
  3. manifest 权限清单要跟代码用到的 API **逐项对照**一遍

## [P022] 小米原生互传的 P2pInfo 比 CatShare 多 5 个字段
- **现象**：小米 15 通过 BLE 写来的 JSON 含 `freq` / `G` / `M` / `P` / `transfer_mode`，
  而 CatShare 的 `P2pInfo` **完全没有**这些字段
  ```json
  {"id":"7d1a","mac":"...","port":57832,"freq":2412,"G":1,"M":1,"P":2,
   "ssid":"...","psk":"...","key":"MFkw...","transfer_mode":0}
  ```
- **含义**：说明对面跑的是**小米原生互传联盟协议**，是 CatShare 实现的**超集**
  （`freq`=频段MHz 2412/5745；`G`/`M`/`P` 疑似 GO capability/mode/preference）
- **处理**：`P2pInfo` 增加这 5 个字段，**解析时容忍缺失**（`optInt(...,0)`），
  发送时按需带上 `freq` / `transfer_mode`
- **启示**：**互传联盟协议 ≠ CatShare**。CatShare 只是其中一个实现，
  真机联调要以**小米实际发来的报文**为准
