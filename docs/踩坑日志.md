## [P001] MAC 地址是死字段，root/Shizuku 完全不需要
- **发现时间**：2026-10-15
- **现象**：CatShare 原版显示"Root 不可用"仍能正常互传；作者为此引入了 Shizuku + root 双路径共 140 行代码
- **根因**：协议里 `P2pInfo.mac` 字段**写了但从不读**。
  - 发送端 `P2pSenderService.kt:432` `mac = cipher?.encrypt(p2pMac)` —— 加密后发出去
  - 接收端 `GattServerService.kt:168` `mac = cipher.decrypt(p2pInfo.mac)` —— 解密后赋给 p2pInfo
  - `P2pReceiverService` 建连只用 `ssid`/`psk`/`port`，**`p2pInfo.mac` 引用数 = 0**
- **证据**：全库 `rg -n "\.mac\b" app/src/main/java/` → 仅 1 处命中（就是上面那个解密赋值）
- **解法**：新项目**彻底不实现 MAC 获取**，删掉 Shizuku/root 依赖
- **收益**：省掉 ~200 行代码 + 一个 20 秒超时的 Service 绑定流程

## [P003] aapt2 用 $HOME/android.jar 报 "attribute not found"
- **现象**：
  ```
  AndroidManifest.xml:3: error: attribute android:minSdkVersion not found.
  ```
  且输出 base.apk 为 **0 字节**
- **根因**：`$HOME/android.jar` 是 **javac 用的 classpath jar，不含资源表**；aapt2 需要用真实 framework
- **解法**：`aapt2 link -I /system/framework/framework-res.apk`
- **记忆点**：
  - `javac -cp` → `$HOME/android.jar`
  - `aapt2 link -I` → `/system/framework/framework-res.apk`
  - **两者不能混用**

- **根因**：d8 **不会自动创建**输出目录（与 javac 的 `-d` 不同）

## [P005] 签名/重打包时 resources.arsc 和 .so 必须 Stored
- **现象**：`INSTALL_FAILED_INVALID_APK: Failed to extract native libraries, res=-2`
  和 `... resources.arsc ... stored uncompressed and aligned on a 4-byte boundary`
- **根因**：`targetSdk >= 30` 且 `extractNativeLibs=false` 时，系统要求特定条目**不得压缩**
- **解法**：打包时用 `zip -0`（Stored）处理 `resources.arsc` 与 `lib/**/*.so`，再 `zipalign -f 4`
- **注**：本项目 MVP 不含 .so，但仍需保证 resources.arsc 为 Stored

## [P006] smali 手写代码极易踩寄存器坑
- **现象**：`java.lang.VerifyError: ... onCreate ... 'this' argument 'Reference: java.lang.String' not instance of 'Reference: moe.reimu.catshare.MainActivity'`
- **根因**：在 `.registers 2` 的方法里用 `v0` 当临时寄存器，**覆盖了后续要当 `this` 用的寄存器**
- **解法**：`.registers 3` + 专用 scratch 寄存器；**更根本的解法是不要手写 smali**
- **结论**：新项目用 Java 源码 → javac → d8，彻底避开此坑

## [P010] build.sh 静默失败：javac 报错仍产出"成功"的 APK
- **现象**：javac 编译失败（1 error），但 build.sh 继续走完 6 步并报告"✅ 构建完成"，产出 12873 字节的 APK
- **根因**：`javac ... 2>&1 | grep -v "^Note:" || true` —— **管道会把 javac 的退出码换成 grep 的**，
  加上 `|| true`，`set -e` 永远不会触发
- **解法**：改为 `if ! javac ... >"$OUT/javac.log" 2>&1; then 打印并 exit 1; fi`
- **教训**：**任何 `cmd | grep` 都会吞掉 cmd 的退出码**。构建脚本里判断成败必须用 `if !` 或 `PIPESTATUS`

## [P012] KeyAgreement.generateSecret(String) 编译桩与运行时返回类型不一致
- **现象**：`error: incompatible types: SecretKey cannot be converted to byte[]`
- **根因**：Android 的 `android.jar` 桩里 `generateSecret(String)` 返回 `SecretKey`，
  但**运行时 Conscrypt 实际返回 `byte[]`**
- **解法**：用 `Object` 接收后 `instanceof` 分支
  ```java
  Object secret = ka.generateSecret("TlsPremasterSecret");
  byte[] keyBytes = (secret instanceof byte[]) ? (byte[]) secret
                  : ((javax.crypto.SecretKey) secret).getEncoded();
  ```
- **验证**：真机 T3 加密自检通过 → 运行时确实走 `byte[]` 分支

## [P014] github.com:443 被墙，但 api.github.com 可达 → git push 永久卡住
- **现象**：
  - `curl https://api.github.com/...` ✅ 正常（能建仓库、能查 API）
  - `git push https://github.com/...` ❌ `Failed to connect to github.com:443 after 31592 ms`
  - 第一次尝试用 credential helper 时**无输出卡死 60 秒以上**
- **根因**：
  1. **`github.com:443` 与 `codeload.github.com` 在本网络不可达**，而 `api.github.com` 走的是不同 IP/链路，可达
  2. credential helper 里引用了**未 export 的 `$GH_TOKEN`**，git 拿到空密码后静默等待输入
- **可达性实测**：
  | 端点 | 状态 |
  |---|---|
  | `api.github.com:443` | ✅ |
  | `github.com:443` | ❌ |
  | `codeload.github.com` | ❌ |
  | `ssh.github.com:443` | ✅ |
  | `github.com:22` | ✅ |
- **解法（本项目采用）**：改用 **Git Data API 推送**，全程只走 `api.github.com`
  ```sh
  GH_TOKEN=xxx GH_REPO=owner/name node scripts/api-push.mjs
  ```
  流程：`POST /git/blobs`（逐文件 base64）→ `POST /git/trees` → `POST /git/commits` → `PATCH /git/refs/heads/main`
- **备选**：SSH over 443（`ssh.github.com:443` 可达），需先把公钥注册到 GitHub 账号

### 连带踩的坑
- **空仓库无法建 blob**：`POST /git/blobs` → `409 Git Repository is empty`。
  必须先用 **contents API** 建一个占位文件（如 `.gitkeep`）让仓库非空：
  ```sh
  curl -X PUT "$API/contents/.gitkeep" -d '{"message":"init","content":"","branch":"main"}'
  ```
- **ref 已存在**：`POST /git/refs` → `422 Reference already exists`。应先 `PATCH /git/refs/heads/main`
- **中文文件名被八进制转义**：`git ls-files` 输出 `"docs/\345\215\217..."` 导致 `ENOENT`。
  必须加 `-c core.quotepath=false`：
  ```js
  execFileSync('git', ['-c','core.quotepath=false','ls-files'])
  ```

## [P016] P2P 建组："第一个" CONNECTION_CHANGED 广播是中间态，会提前放行
- **现象**：`createGroup` 返回成功，但 `getSession()` 为 `null`，日志显示"会话信息尚未就绪"
- **根因**：`WIFI_P2P_CONNECTION_CHANGED_ACTION` **会来两次**：
  ```
  16:16:05.134  groupFormed=false  group=null          ← 中间态（组还没真正建好）
  16:16:05.167  createGroup 的 ActionListener 回调成功
  16:16:05.497  groupFormed=true   group=DIRECT-xxx    ← 真正的组信息（晚 330ms）
  ```
  用 `CountDownLatch` 等"第一个"广播 → 被 `groupFormed=false` 提前放行
- **解法**：不要等"广播到达"，要等"**状态就绪**"：
  ```java
  private void awaitGroupReady(int timeoutSec) {
      long deadline = System.currentTimeMillis() + timeoutSec * 1000L;
      while (System.currentTimeMillis() < deadline) {
          if (lastSession != null) return;   // group 非空才算就绪
          Thread.sleep(100);
      }
  }
  ```
- **教训**：Android 的 `*_CHANGED` 类广播常伴随**中间态**（值还是旧的/空的）。
  判断就绪要看**内容**，不要看**次数**

## [P018] BLE 特征值读写必须支持分块（默认 MTU 只有 23 字节）
- **现象**：`DeviceInfo`（含 124 字节 Base64 公钥）远超默认 ATT MTU，一次读不完
- **根因**：BLE 默认 ATT MTU = 23 字节，净荷仅 **20 字节**。
  读写长属性时系统会按 offset 多次请求
- **解法**（两层都要处理）：
  ```java
  // 服务端：按 offset 切片返回，用 GATT_INVALID_OFFSET(0x07) 拒绝越界
  byte[] piece = Arrays.copyOfRange(snapshot, offset, snapshot.length);
  server.sendResponse(device, requestId, 0, 0, piece);

  // 服务端：累积分块写入（preparedWrite=true 时继续等）
  System.arraycopy(value, 0, buf.data, offset, value.length);
  if (preparedWrite) return;          // 还有后续分片
  byte[] full = Arrays.copyOfRange(buf.data, 0, buf.length);

  // 客户端：协商 MTU 后再传，onCharacteristicWrite 驱动下一片
  g.requestMtu(517);
  // onMtuChanged → writeChunkSize = mtu - 3
  ```
- **注意**：`onDescriptorWriteRequest` **必须回 sendResponse**，否则对端订阅时超时

## [P021] ★致命★ 缺 `INTERNET` 权限 → 所有 socket 操作 EPERM
- **现象**：BLE 发现、GATT 读写、ECDH 解密、WiFi Direct 加入组**全部成功**，
  一到建 socket 就挂：
  ```
  ❌ java.net.SocketException: socket failed: EPERM (Operation not permitted)
  ```
  这个报错极具误导性 —— 看起来像 SELinux 或 root 问题，其实是**权限没声明**
- **根因**：`AndroidManifest.xml` 里**没有** `<uses-permission android:name="android.permission.INTERNET" />`。
  Android 上**任何** socket（包括 `127.0.0.1` 回环、`ServerSocket` 监听）都需要 INTERNET 权限；
  没有它就返回 `EPERM`
- **为什么没早发现**：M1/M2 只测到 BLE 和 WiFi Direct，**从没真正开过 socket**。
  M3/M4 引入 HTTP 服务 + WS 连接后第一次碰 socket，才暴露
- **解法**：
  ```xml
  <uses-permission android:name="android.permission.INTERNET" />
  ```
- **验证方法**（已内置为自检）：
  ```java
  // net/SocketSelfTest.java —— 起回环 ServerSocket+Socket，返回 null 表示正常
  ```
  真机日志：`HuChuan.SocketTest: socket 自检通过: ok`
- **教训**：
  1. **`EPERM` on socket ⇒ 先查 INTERNET 权限**，不要往 SELinux/root 方向查
  2. 每个新引入的系统能力（这里是网络）都要**立刻做自检**，别等联调
  3. manifest 权限清单要跟代码用到的 API **逐项对照**一遍

## [P022] 小米原生互传的 P2pInfo 比 CatShare 多 5 个字段
- **现象**：小米 15 通过 BLE 写来的 JSON 含 `freq` / `G` / `M` / `P` / `transfer_mode`，
  而 CatShare 的 `P2pInfo` **完全没有**这些字段
  ```json
  {"id":"7d1a","mac":"...","port":57832,"freq":2412,"G":1,"M":1,"P":2,
   "ssid":"...","psk":"...","key":"MFkw...","transfer_mode":0}
  ```
- **含义**：说明对面跑的是**小米原生互传联盟协议**，是 CatShare 实现的**超集**
  （`freq`=频段MHz 2412/5745；`G`/`M`/`P` 疑似 GO capability/mode/preference）
- **处理**：`P2pInfo` 增加这 5 个字段，**解析时容忍缺失**（`optInt(...,0)`），
  发送时按需带上 `freq` / `transfer_mode`
- **启示**：**互传联盟协议 ≠ CatShare**。CatShare 只是其中一个实现，
  真机联调要以**小米实际发来的报文**为准

## [P023] ★致命★ 传输层必须是 TLS（HTTPS/WSS），不是明文 HTTP
- **现象**：真机联调时对方在"已加入组"之后就不再请求；我们起的是明文 HTTP 服务
- **根因**：CatShare 发送方用 Ktor **`sslConnector` + 自签名证书**：
  ```kotlin
  val keyStore = buildKeyStore { certificate("sampleAlias") { ... } }
  sslConnector(keyStore, keyAlias="sampleAlias", ...) { port = 0 }
  ```
  与之对应，接收方：
  ```kotlin
  sslSocketFactory(sslContext.socketFactory, FakeTrustManager())
  hostnameVerifier { _, _ -> true }
  ```
  即：**传输层是 TLS，但证书内容不被校验**。小米原生互传同样走 https/wss。
- **解法**：发送方必须提供 TLS
  ```java
  // 服务端：用随包分发的自签名证书
  SSLContext sctx = Tls.serverContext(ctx);          // 加载 res/raw/huchuan.p12
  transfer.startHttpServer(true, sctx);              // HTTPS
  transfer.startWsServer(wsPort, sctx);              // WSS

  // 客户端：信任一切 + 放行主机名
  SSLContext cctx = Tls.clientContext();
  ```
- **证书来源**：Android **没有公开的 X.509 证书生成 API**，所以证书是构建期用
  `keytool -genkeypair -keyalg EC -groupname secp256r1` 生成后放进 `res/raw/`。
  它对端本来就不校验，内容无所谓，**关键是有 TLS 握手**
- **验证**：JVM 端到端测试 —— TLS 握手成功（`TLS_AES_256_GCM_SHA384`）→ HTTPS 200 →
  2MB 字节级一致

## [P024] /download 返回的是 **ZIP 流**，不是裸文件
- **现象**：即使走通 HTTPS，按裸字节收下来的文件对方也解不开
- **根因**：CatShare 的 `/download` 用 `ZipOutputStream` 打包：
  ```kotlin
  call.respondOutputStream(ContentType.Application.Zip, HttpStatusCode.OK) {
      ZipOutputStream(this).use { zo ->
          zo.putNextEntry(ZipEntry("$i/${rf.name}"))    // 条目名 = "序号/文件名"
  ```
  接收方用 `ZipInputStream` 解开（`saveArchive`）
- **解法**：发送端 `ZipOutputStream` 打包，条目名 `"0/" + 文件名`；
  接收端 `ZipInputStream` 解包并取条目名最后一段
- **注意**：ZIP 长度事先未知，HTTP 头用 **`Transfer-Encoding: chunked`**
  （不能给 `Content-Length`）

## [P025] WS 端点路径是 `/websocket`，不是 `/`
- **证据**：`val wsSession = client.webSocketSession("wss://${hostPort}/websocket")`
- **解法**：服务端 `startServer(port, "/websocket", ...)`，客户端 `connect(host, port, "/websocket", ...)`
- **教训**：三个端点要素都要对齐 —— **协议(scheme) + 路径(path) + 端口(port)**，
  少一个都连不上，且报错往往不指向真正原因

## [P026] ★致命★ status 必须在收到 sendRequest 后**立刻**回，对端只等 10 秒
- **现象**（真机日志）：
  ```
  17:09:15.478  ← action:0:versionNegotiation?{"versions":[1],"version":1}
  17:09:15.478  → ack versionNegotiation          ← 我们回了
  17:09:25.259  连接关闭                            ← 恰好在 +10s
  17:09:25.408  P2pStateMachine.handleGroupRemoved  ← 对方撤了组
  ```
  TLS/WSS/版本协商**全部成功**，然后就静默断开
- **根因**：CatShare 接收方等用户确认用的是
  ```kotlin
  val userResponse = withTimeoutOrNull(10000L) { waitForAction(localTaskId) }
  if (userResponse != true) { sendStatus(99, taskId, 3, "user refuse"); throw CancelledByUserException() }
  ```
  **10 秒是对方的确认窗口**。超时即视为拒绝并 `removeGroup` 断开。
  我们虽然回了 status，但**晚于对方的等待窗口**（或 id/时序不匹配），于是被判超时
- **解法**：收到 `sendRequest` 后**立即**回 status，再去下载
  ```java
  JSONObject req = recv.awaitSendRequest(20);
  recv.respond(taskId, 99, 1, "ok");    // ★ id=99，与 CatShare sendStatusIgnoreException(99,...) 一致
  recv.download(...);                    // ★ 紧接着就下载
  ```
- **另一个隐含约束**：发送方的 `transferStartFuture` 等的是**接收方真的发起 /download**，
  超时 30 秒（`awaitWithTimeout(30s, "Waiting for start transfer")`）。
  所以 **status 和 download 之间不能有任何耗时操作**
- **验证**：写了 CatShare 发送方时序的完整模拟（TLS + /websocket + status(99) + HTTPS ZIP），
  1MB 字节级一致

## [P031] LD_LIBRARY_PATH 在扩展工具间的冲突（反复踩）

## [P036] ★ 手写 smali 的寄存器类型冲突 —— 同一个 VerifyError 犯了两次
- **现象**：
  ```

  register v4 has type Reference: java.lang.String but expected Integer
  ```
- **直接原因**：我在一个方法里把同一寄存器先后当不同类型用：
  ```smali
  const-string v4, "taskId"          # v4 = String
  const-high16 v5, 0x4000000         # v5 = int
  ...
  invoke-static {..., v6, v5}        # v5 又当 int 传给 getBroadcast
  move-result-object v5              # v5 变成 PendingIntent
  sget v6, R$drawable;->ic_downloading:I   # v6 从 Intent 变成 int
  move-result-object v6              # v6 又变成 Builder
  ```
- **根本原因**：**smali 汇编器不做寄存器类型检查，ART 的验证器才做。**
  所以"编译通过"完全不代表"能跑"。
- **最阴险的一次**：以为某个寄存器"已经没用了"就可以复用，但它在**后面**还被引用：
  ```smali
  # v0 在 456 行还是 Intent
  invoke-static {p0, p1, v0, p6}, Landroid/app/PendingIntent;->getBroadcast(...)
  # 我在 472 行把 v0 当 String 用 → 冲突
  move-object v0, p2
  ```
  **判断寄存器是否可复用，必须看它在整个方法里的完整生命周期，不能只看插入点附近。**
- **正确做法（按推荐顺序）**：
  1. **能用 Java 就用 Java** —— `javac` + `d8`，编译器保证类型正确（P028 的教训）
  2. 必须手写 smali 时：
     - **一个寄存器只装一种类型**，绝不复用
     - 需要临时寄存器就**先把 `.registers` 调大**（如 11 → 14），用全新的 `vN`
     - **改完必须用 `d8` 复验**：
       ```sh
       java -cp $D8_JAR com.android.tools.r8.D8 --output /tmp/out --lib $HOME/android.jar new.dex
       # 无输出 = 通过；报错就是真有问题
       ```
       `d8` 用的是同一套校验规则，能在安装前抓住这类错误。
- **教训**：
  - `smali` 汇编成功 ≠ 字节码合法
  - **每次改完 smali，必须跑一遍 d8 校验再打包**（当时我跳过了这步，直接装机 → 崩）
  - 崩溃出现在"真实传输时"而不是启动时，因为 ART 是**懒验证**（用到才验证），
    所以启动测试通过也说明不了问题

## [P038] ★★★ 手写 smali 的致命陷阱：`.registers` 决定 pX 映射，改它 = 全盘洗牌
- **连续两次崩溃的真正根因**（P036 的诊断是错的，特此更正）
- **smali 寄存器映射规则**（必须背下来）：
  ```
  .registers N，方法有 K 个参数（含 this）
  → 参数寄存器 p0..p(K-1) 占据 v(N-K) .. v(N-1)
  → 纯局部寄存器只有 v0 .. v(N-K-1)
  ```
- **我犯的错**：原方法 `.registers 11`（9 个参数 → p0=v2，局部只有 v0,v1）。
  我为了"腾出临时寄存器"把它改成 `.registers 14`，
  结果 p0 从 v2 变成 v5 —— **所有 pX 的物理寄存器全部平移**。
  原始代码里针对 v2/v7 等具体编号成立的类型关系被打乱 → VerifyError。
- **第二次更蠢**：`.registers 17`，9 个参数 → p0=v8。
  我用了 v8,v9,v10,v11,v12 当"局部寄存器"，
  **它们其实全都是参数寄存器**（v8=p0 Context，v9=p1 taskId…）。
  把 taskId(int) 当 PendingIntent 用 → ART 报
  `register v9 has type Reference: PendingIntent but expected Integer`
- **正确做法**：
  1. **先算清楚**：局部区 = `v0 .. v(N-K-1)`，只用这个区间内的寄存器
  2. 需要更多局部寄存器 → **调大 `.registers`，同时重新计算 pX 起点**
     （不要以为"原来的 pX 还在原地"）
  3. **最稳妥**：`.registers` 设得足够大（如 20），
     让局部区（v0..v10）与参数区（v11..v19）完全分离，绝不重叠
- **为什么 d8 校验骗了我**：d8 的输入是 dex 时，它只做自己的 IR 转换，
  **不运行 Android 的 verifier**。"d8 无输出"是假阳性，不能作为验证依据。

## [P044] ★★★ 用 kotlinc 编译的类直接替换进 APK 会崩 —— R8 已删除大量 API
**结论：不要用 kotlinc 编译整包替换。** 这个 APK 被 R8 激进压缩过，
编译期依赖库里的 API 与运行时 APK 里的**不是同一套**。

### 实测到的三类不兼容（全都会导致运行时崩溃）

**1) 静态工厂方法被删**
```
NoSuchMethodError: No method NotificationManagerCompat.from(Context)
```
编译期 androidx 里有 `from()`；运行时 APK 里 `NotificationManagerCompat`
**只剩 3 个成员**：`<init>(Context)`、`notify(int,Notification)`、字段 `mNotificationManager`。
原版源码里的 `from(ctx)` 被 R8 内联成了 `new NotificationManagerCompat(ctx)`。

**2) 构建器/DSL 函数被删**
```
NoSuchMethodError: No virtual method Json.getSerializersModule()
```
编译期 `Json.serializersModule` 是 **private 字段 + public getter**；
运行时 APK 里是 **public 字段、无 getter**。方向正好相反。
`JsonKt`（即 `Json { }` DSL）、`JsonBuilder.setIgnoreUnknownKeys` 运行时全都不存在。

**3) API 被内联成字段直写**
```smali
# 原版（R8 优化后）
iput-object p2, p5, Landroidx/core/app/NotificationCompat$Builder;->mContentTitle:Ljava/lang/CharSequence;
# 而不是
invoke-virtual {p5, p2}, ...->setContentTitle(...)
```
运行时 `NotificationCompat$Builder` 只剩：
`<init> / addAction / build / limitCharSequenceLength / setFlag / setStyle`
—— `setContentTitle`、`setLargeIcon`、`setDeleteIntent` 全被删了，只能写字段。

### 怎么判断哪些 API 还能用（可复用脚本）
不要靠 `strings`/子串搜索（dex 的字符串池与方法表是分开的，会误判）。
**直接解析 dex 的方法表**：
```python
# dex 头偏移：string_ids(56) type_ids(64) proto(72) field(80) method(88) class_def(96)
sid_n, sid_o = struct.unpack_from('<II', d, 56)
tid_n, tid_o = struct.unpack_from('<II', d, 64)
mid_n, mid_o = struct.unpack_from('<II', d, 88)
# method_id_item = (class_idx:H, proto_idx:H, name_idx:I)
```
拿到 `Lcls;->name` 全集后，逐个核对**我们编译产物引用的每个方法**。
注意要沿着 `class_def.superclass_idx` 向上找（继承方法不在子类自己的表里）。
脚本：`$HOME/kotlin-build/verify3.py`

### ✅ 正确做法：只改方法体，别整类替换
最终可行的方案（本机验证 0 崩溃）：
1. 用 baksmali 反编译**原始 APK**，作为基底（`/tmp/orig2/smali`）
2. 找到要改的方法，**照抄它的风格**（R8 内联后的写法）
3. 只替换**这一个方法**，其余 89 个类全部还原成原版
4. 结果：整个 APK **只有 1 个文件与原版不同**

### 关键坑：`.registers` 与参数寄存器
原版方法 `.registers 11` + 9 个参数 → 只有 `v0`、`v1` 是可自由使用的局部寄存器，
`v2..v10` 全是参数寄存器。**改 `.registers` 会整体平移 `pX` 的映射**，
必须同步改所有 `pX` 引用（详见 P038）。

## P046 ★ 设备身份用错 MAC —— 对端显示「未识别的设备」

**现象**：小米15 能发现本机并显示名称「Xiaomi 12 Pro」，但标记为**未识别的设备**；
本机可以主动发给小米15，**但小米15 发不过来**（能发不能收）。

**根因**：CatShare 读 `p2p0` 接口拿 MAC 作为设备身份写入 BLE GATT 特征值：

```json
{"state":7,"key":"<公钥>","mac":"66:dd:e9:a7:fb:17","catShare":7}
```

但 `p2p0` 是 **WiFi Direct 虚拟接口**，其 MAC 是**随机化**的：

| 接口 | MAC | 性质 |
|---|---|---|
| `p2p0` | `66:dd:e9:a7:fb:17` | 首字节 0x66，本地管理位=1 → **每次开机都变** |
| `wlan0` | `64:dd:e9:25:fb:17` | 真实硬件地址，稳定 |

随机 MAC 导致对端**无法把本机匹配到已知设备库**，因此判为「未识别」，
并拒绝向它推送数据 —— 这正是「能发不能收」的原因。
（发送是主动发起，不需要对端先认出你；接收必须对端认得出你。）

**修复**：三处 `"p2p0"` → `"wlan0"`
```
services/GattServerService.smali              (身份广播)
services/MacAddressService.smali              (getP2pMacAddress)
services/P2pSenderService$runTask$2.smali     (发送时广播本机 MAC)
```

**关键验证：这个 MAC 不参与 P2P 连接**，只作身份标识 ——
`WifiP2pConfig.Builder` 只调用了 `setGroupOperatingBand` / `setNetworkName` /
`setPassphrase` / `enablePersistentMode`，**没有 `setDeviceAddress`**。
所以改 MAC 不会影响 P2P 建组，是安全的。

**验证**：改后日志 `Updating local MAC address to 64:dd:e9:25:fb:17` ✅

## P047 ★ 磁贴「只亮一下」——广播被 signature 权限挡掉

**现象**：点磁贴后只闪一下，不保持高亮，无法据此判断接收服务是否在跑。

**根因**：`registerInternalBroadcastReceiver` 注册时带了签名级权限：

```smali
registerReceiver(receiver, filter,
                 "moe.reimu.catshare.INTERNAL_BROADCASTS",  ← protectionLevel=signature
                 null, flags)
```

而 `GattServerService` 回复状态时用的是**不带权限**的 `sendBroadcast(intent)`。
Android 规则：接收方声明了权限，发送方必须持有，否则广播被系统丢弃。
→ 磁贴永远收不到 `UPDATE_RECEIVER_STATE` → 无法点亮。

雪上加霜的是 `onStartListening` 第一件事是 `setState(false)`（强制熄灭），
所以表现为「亮一下又灭」。

**修复**：
1. `PermissionUtilsKt.registerInternalBroadcastReceiver`：权限参数改为 `null`
   （纯内部广播，未 exported，无外部风险）
2. `ReceiverTileService.onStartListening`：删掉 `setState(false)`，保持现状等真实状态

**排查提示**：`cmd statusbar expand-settings` 会开到**虚拟副屏**上，
在双屏环境下验证磁贴必须指定物理屏，否则测了个寂寞。

## P048 ★★ 「接收完成」和「接收中断」同时弹 —— 是原版 bug

**现象**：文件接收成功、弹出「接收完成」，**同时**又弹一条「接收中断」。

**排查过程（重要：先证明是原版问题）**：
把 APK 换回**未改动的原版**（MD5 `d32a3e31…` 校验一致）后复现 → **确认原版就有此 bug**。

抓到的堆栈（两次接收，两次相同）：
```
E StandaloneCoroutine: Failed to process task
E StandaloneCoroutine: java.io.EOFException
    at okio.RealBufferedSource.require
    at okio.RealBufferedSource.readByte
    at okhttp3.internal.ws.WebSocketReader.readHeader
    at okhttp3.internal.ws.RealWebSocket.loopReader     ← WS 读取循环
```

**根因**：`P2pReceiverService` 的接收协程：

```smali

    startForeground(2, 准备中通知)
    runReceive(info, localTaskId)
:try_end_46
    .catch CancelledByUserException → :catch_16
    .catchall                      → :catchall_14  →  :goto_58
```

对端传完文件后**正常关闭 WebSocket** → okhttp 的 `loopReader` 抛 `EOFException`
→ 被 `.catchall` 捕获 → 走 `:goto_58` → `Log.e` + 弹「接收中断」。

**但文件已经收完了**，所以成功通知和失败通知**同时**出现。

时间线佐证（`p2p0 DISCONNECTED reason=3 locally_generated=1` = 本地主动拆组）：

```
02:22:08.032  wpa_supplicant: p2p0 CTRL-EVENT-DISCONNECTED (本地主动)
02:22:08.038  NotificationService: 取消前台通知 id=2
```

**关键认知**：`EOFException` 在 `RealWebSocket.loopReader` 里 = **连接正常关闭**，
不是故障。okhttp 就是这么设计的，调用方必须自己识别。

**修复**（`P2pReceiverService$onStartCommand$job$1.smali`，`:goto_58` 入口）：
```smali

    → Log.i("WebSocket closed normally (EOF)")
    → goto :goto_49        # 正常结束路径（stopForeground + clearBusy）
:not_eof
    → 原有 Log.e + 弹通知    # 真正的错误仍会提示
```

**顺带纠正一个误解**：`createFailedNotification` 里的 `verbose` 开关
**不控制"是否显示通知"**，两个分支都会弹，只是 `verbose=true` 时额外显示堆栈。

## P049 ★★ 教训：「只改了方法体」不等于「只改了方法体」

**事故**：为改通知样式，最终 APK 相对原版实际改动了 **8 个类 + 16 个新增类**，
而我一直以为只改了「3 个通知方法」。用户反馈「原版能用，你改了就不能用」时，
我仍坚信"没碰传输逻辑"，于是连续往错误方向猜（app 选错 / 广播权限 / MAC），
浪费多轮。

**为什么会产生 16 个新增类**：smali 反汇编 → 重新汇编时，
R8 生成的合成类（`$$ExternalSyntheticLambda0`、`$0` 等）会被 smali **重新命名和生成**。
它们通常无人引用、无害，但**会让「我改了什么」的清单严重失真**。

**正确做法**：
```bash
# 每次打包前，逐文件比对，得到真实的改动清单
for f in $(cd src && find . -name "*.smali"); do
  diff -q "src/$f" "orig/$f" >/dev/null || echo "改: $f"
done
```
**并且**：要加新改动时，**从原版 smali 树重新复制一份干净基线**，
只打那一个补丁，而不是在积累了大量改动的树上继续叠。

**验证成品的方法**（本次采用）：
反编译**已安装**的 APK，对全部类逐一比对原版，确认"只有 N 个文件不同"，
而不是只检查自己以为改过的文件。

## P050 ★★★ VerifyError: register v4 has type Boolean but expected Reference

**事故**：P048 的 EOF 修复第一版，装机后**每次接收都崩溃**（用户："一直崩溃"）。

```

  P2pReceiverService$onStartCommand$job$1:
  [0x89] register v4 has type Boolean but expected Reference: java.lang.String
```

**根因**：我在异常处理入口插入了

```smali
instance-of v4, p1, Ljava/io/EOFException;   # v4 ← Boolean

if-eqz v4, :not_eof

invoke-static {p0}, ...->getTAG(...)Ljava/lang/String;
move-result-object v4                        # ❌ v4 ← String —— 类型冲突！
```

同一个寄存器**先当 Boolean 又当 String** → ART 验证器直接拒绝整个类。

**关键点：这不是"运行时才出错"，而是类加载时就被拒绝** ——
所以表现为"一启动接收服务就崩溃"，而不是偶发。

**正确做法：寄存器的类型在其整个生命周期内必须一致**

```smali
instance-of v4, p1, Ljava/io/EOFException;   # v4 只做 Boolean

if-eqz v4, :not_eof

invoke-static {v0}, ...->getTAG(...)Ljava/lang/String;
move-result-object v0                        # ✅ 用 v0（本来就是 String）
const-string v1, "WebSocket closed normally (EOF)"
invoke-static {v0, v1}, Landroid/util/Log;->i(...)I
```

**教训**：
1. 改 smali **不能只看指令语义，必须看寄存器类型**。
   `move-result-object vX` 会把 vX 标成对象类型，若之前是 int/boolean 就冲突。
2. **插桩优先复用"已经是目标类型"的寄存器**，不要随手拿一个空闲编号就用。
3. 验证手段：反编译回 smali，`grep "move-result-object v4"` 确认 v4 没有既做比较又做对象。
   （更稳的是装机跑一次 —— ART 验证器是最终裁判。）

**同时暴露的流程问题**：这次崩溃**本可以避免** ——
我在此前多次改动中已经踩过同类坑（P044 记录过「.registers 改变导致 pX 映射错位」），

## P052 ★★★ 三次崩溃的完整教训：改 smali 必须做寄存器类型检查

同一个补丁崩了两次，第三次才成功。三次的错误各不相同，但根因是同一个 ——
**我只检查"指令语义"，没检查"寄存器类型在数据流上是否自洽"**。

| 版本 | 错误 | 原因 |
|---|---|---|
| 1 | `[0x89] register v4 has type Boolean but expected Reference: String` | `v4` 在本方法必须是 String（供 `throwUninitializedPropertyAccessException(String)` 用），我拿它做 `instance-of` |
| 2 | `[0x8C] thrown value of non-reference type Boolean` | 改用 `v3`，但 `v3` 被 `throw v3` 使用 → 必须是引用类型 |
| 3 | ✅ 成功 | 新增独立方法 `isEof()`，调用处只 `move-result v6`，该点在数据流上是死寄存器 |

**我犯的检查方法错误**：
写了个脚本统计"每个寄存器被赋过哪些类型"，得到 `v3: int` 就以为安全 ——
**但 `throw v3` 不是赋值指令，脚本没覆盖它**，于是一个要求引用类型的用法被漏掉。

**正确的检查清单**（改 smali 前必做）：
1. **列出该寄存器的所有使用**，不只是赋值：
   `grep -nE "(^|[ ,{])vN([ ,}]|$)"` —— 覆盖 `throw` / `invoke` / `if-*` / `move-result*`。
2. **区分"赋值类型"和"使用要求"**：
   - `move-result-object vX` → 要求 vX 是本指令之后的对象
   - `throw vX` → 要求 vX 是引用
   - `invoke-static {vX}, ...(Ljava/lang/String;)` → 要求 vX 是 String
3. **确认新寄存器在所有到达路径上都是死的**：
   - 检查是否存在绕过你的代码块的 `goto`（本例是 `goto :goto_b0`）。
4. **最可靠的做法：不改现有方法的寄存器分配，新增独立方法**。
   有自己的 `.registers`，零冲突风险。**优先选这个。**

**验证顺序**（不能跳）：
```
改 smali → 汇编成功   ← 这只证明语法对，不证明能加载
```

## P053 ★★ 不要用 `am start-foreground-service` 测这个 app —— 会污染 busy 锁

`P2pReceiverService.onStartCommand` 的逻辑：

```smali
invoke-virtual {p3}, MyApplication;->setBusy()Z    # 先占锁
if-nez p3, :cond_22
    → "Application is busy, skipping" + return      # 已被占 → 永久拒绝
:cond_22
getParcelableExtra("p2p_info")
if-nez p1, :goto_2c
:goto_2c
    return p2                                        # ❌ 没有 p2p_info 就 return，不 clearBusy
```

**用 `am start-foreground-service` 不带 `p2p_info` extra → 必然泄漏 busy 锁**
→ 之后所有接收都被 `"Application is busy, skipping"` 拒绝，表现为**"点了完全没反应"**。

**这个状态极难排查**，且只能靠 force-stop 重启进程解除（标志在内存里）。

**教训**：
- 测试这个 app **不要**用 `am` 命令模拟，它会制造假故障。
  **让用户走真实流程**，或者用 `am start` 启动 `StartReceiverActivity`（它只起 `GattServerService`，安全）。
- 每次测试后 **`am force-stop` 复位**，避免把 app 留在坏状态。
- 如果真的需要带 extra 启动，必须提供合法的 `p2p_info` Parcelable。

**顺带：这本身也是原版的一个真实缺陷** —— 无 `p2p_info` 的启动路径漏了 `clearBusy()`。
如果将来要修，在 `:goto_2c` 前加 `clearBusy()` 即可（低风险）。

## P054 · build.sh 有两处必然失败的环境问题（已修）

**现象**：`./build.sh` 在 [4/6] 打包处静默产出 17KB 的假 APK，[6/6] 签名再报
`dlopen failed: library "libandroid-shmem.so" not found`，最终 `cp: bad ...`。

**两个独立原因**：

1. **本机 `zip` 不可用**
   `CANNOT LINK EXECUTABLE "zip": library "libbz2.so.1.0" not found`。
   `zip -q -j base.apk dex/classes.dex` 失败后 `set -e` 竟然没中止（在子 shell 里），
   于是 `base.apk` 保持 aapt2 产出的 8KB 骨架 → 对齐/签名后 17KB 的"APK"。
   **改用 python3 zipfile 打包**（`python3` 在本机可用）。

2. **`LD_LIBRARY_PATH` 没设**
   `apksigner` 是 java 程序，它的 JVM 需要 engine/lib 下的 `libandroid-shmem.so`。
   脚本里从未设置，于是 `apksigner` 一启动就 dlopen 失败。
   **在脚本开头统一导出** `engine/lib:android-buildtools/lib:python/lib`。

**教训**：`set -e` **不会**捕获子 shell 内的失败。打包这种关键步骤要显式检查产物大小
（正常应 > 60KB），别让一个 17KB 的文件一路走到签名。

**顺带**：`build.sh` 现在改为纯 python 打包，已实测 `./build.sh` 全绿。

## P055 · 分享弹窗必须"认出是哪台设备" —— lastFound 只留最后一台

**背景**：做「系统分享 → 弹卡片选设备」时，`SenderService` 原本是
`while(...) { target = client.getLastFound(); if (target != null) break; }`，
即**扫到谁就发谁**，没有选择。

**坑**：给 `GattClient` 加"按地址取设备"时，如果继续只维护 `lastFound`，
那么目标设备被发现之后，**只要再来一台别的设备，`lastFound` 就被覆盖** →
用户点了 A，结果扫到 B 时 A 丢了 → 表现为"点了没反应"或发错人。

**正确做法**：`GattClient` 用 `LinkedHashMap<address, BluetoothDevice>` 记住**全部**
发现过的设备，`getFound(addr)` 按地址取；并且 `startScan()` 时 `found.clear()`，
避免上一次扫描的陈旧设备泄漏到这一次。

**教训**：扫描类 API 不要只暴露"最后一个"。选择型 UI 必须能按稳定标识（地址）回查。

## P058 · P2pInfo.mac 必须填真实 p2p0 地址，否则对方连不上

**现象**：分享弹窗选中小米15 → 卡片显示"正在发送到 Mi 15" → **然后没有任何反应**。

| | catShare | huchuan（改前） |
|---|---|---|
| `mac` 字段 | `MacAddressService.getP2pMacAddress()`<br>→ `getMacAddressByName("p2p0")` | 写死 `"02:00:00:00:00:00"` |

```smali
# P2pSenderService$runTask$2$1.smali:758
```

```smali
const-string v0, "p2p0"
```

- 失败现象是"超时"时，要看**对端有没有来连**（WS 有没有 accept）。

## P058 修正 · mac 字段的真相（上一版结论是错的）

**上一版我写的**：「mac 必须是真实 p2p0 地址，否则对方连不上」——**这个结论是错的**。

**推翻它的证据**（来自 catShare 自己的日志）：
```
GattServerService: Updating local MAC address to 66:dd:e9:a7:fb:17
```
而 catShare 的 `P2pSenderService$runTask$2.smali` 里：
```smali
const-string v4, "02:00:00:00:00:00"                                     # 默认值
invoke-virtual {...}, Lmoe/reimu/catshare/utils/ShizukuUtils;->getMacAddress(...)
invoke-static {...}, Lmoe/reimu/catshare/utils/RootMacReader;->getMacAddressByName(...)
```
即 **catShare 用 root 读真实 MAC，读不到才回落假值**。

**真正的根因**：huchuan **没有 root 授权**。
```
KernelSU allowlist:
  ✅ moe.reimu.catshare       ← 有授权
  ❌ com.huchuan              ← 没有
```
`NetworkInterface.getHardwareAddress()` 被 SELinux 拒（`avc: denied { search } sysfs_net`），
而 `su` 又没有授权 → 两条路都拿不到 MAC。

**修法**：新增 `com.huchuan.core.RootMacReader`，**逐条照搬** catShare 的 `classes3.dex`：
- 8 个 su 路径候选（`su` / `/system/bin/su` / `/data/adb/ksu/bin/su` / …）
- `probeRoot()` 用 `su -c id` 判断是否含 `uid=0`
- 五级回退：`ip addr show` → `cat /sys/class/net/X/address` → `ip link show` → `ifconfig` → sysfs 直读
- 每级用 `isValidMac()` 校验

**关键教训**：**"没有 root 权限"和"代码写错了"表现完全一样**。
排查时先确认**前提条件**（权限/授权），再怀疑代码。
另外：**catShare 有 root、huchuan 没有** —— 这个差异我一开始完全没注意到。

## P059 · 接收方不能自动回 status(接受)

**现象**：小米15 那边点了「接受」，huchuan 这边却报「对方已取消」。

**原因**：`ReceiverService` 收到 `sendRequest` 后**立刻**回 `status(type=1)`，
根本没等用户点通知。
```
awaitSendRequest(20)          ← 等到 sendRequest
respond(taskId, 99, 1, "ok")  ← 立刻自动接受（错）
```
用户在通知上点「接受」需要几秒，等真正的手势到达时，
对端状态机已经因为我们抢跑的 status 而错位 → 表现成「已取消」。

**修法**：
- 新增 `ReceiverActionReceiver`：接通知按钮的广播
- `ReceiverService.waitForUserDecision()`：弹带 `✕ 拒绝` / `↓ 接收` 的通知，
  每 100ms 轮询 `DECISION`，最多等 60 秒
- 用户点了才回 `status(type=1)`；拒绝回 `type=3, reason="user refuse"`
  （与 catShare 的 `sendStatusIgnoreException(99, …, 3, "user refuse")` 一致）

**教训**：**凡是"需要用户决策"的环节，代码里绝不能自己替用户决定**。
自动接受看起来"更顺畅"，实际是抢在对端预期之前行动，必然错位。

## P060 · WS 和 HTTP 必须共用同一个端口（这是"对方已取消"的真因）

**现象**：小米15 收到 `sendRequest`、用户点了「接受」，huchuan 这边却报
「等待对方确认超时 / 对方未接受」，小米15 那边显示「对方已取消」。

**关键证据**（huchuan 日志，一次完整会话）：
```
WS 客户端已连接
→ versionNegotiation
← ack:0:versionNegotiation          ← 握手正常
→ sendRequest {...}
← ack:1:sendRequest                 ← 对方确认收到
对端断开                             ← 全程 RX 只有这两条
❌ 等待对方确认超时
```
`RX` 从头到尾只有 `ack:0` 和 `ack:1` —— **对方一次 status 都没发**，
而且我们的 `HTTP 请求` / `/download` 日志**一次都没出现过**。

**根因**：我们起了**两个端口**。
```java
int httpPort = transfer.startHttpServer(true, tls);   // 文件下载
int wsPort   = findFreePort();
transfer.startWsServer(wsPort, tls);                  // WS 信令
o.put("port", wsPort);                                // ← 只告诉对方这一个
```
小米15 拿 `port` 连上 WS 后，要去做 `GET /download?taskId=…` ——
它只会用**同一个 port**，于是请求打到 WS 服务上，连不上 → 它判定失败并显示「已取消」。

**CatShare 怎么做**：用 Ktor 的 `embeddedServer`，**一个端口挂两个路由**：
```smali
invoke-static {...}, Lio/ktor/server/engine/EmbeddedServerKt;->embeddedServer$default(...)
const-string p0, "/download"
invoke-static {p1, p0, v0}, Lio/ktor/server/routing/RoutingBuilderKt;->get(...)
```
P2pInfo 里只有一个 `port`，两边自然一致。

**修法**：
1. `Transfer.startUnifiedServer(ctx)`：一个 ServerSocket 同时接两种请求
2. `route(socket)`：先窥探请求行
   - `GET …/websocket` → `MiniWebSocket.upgradeAccepted(...)`
   - 其它 → `serveFile(...)`
3. `SenderService` 只起这一个端口，P2pInfo 里填它

**★实现上的坑★**：窥探首行用的 `PushbackInputStream` **必须一路传下去**。
`Socket.getInputStream()` 每次返回同一个底层流，但**已读走的字节不会回来** ——
若在 `handleServerConn` 里重新调 `s.getInputStream()`，首行就丢了，握手必失败。
所以 `upgradeAccepted` / `handleServerConn` / `serveFile` 都加了「传入已有流」的重载。

**验证**：写了个独立测试，同一端口上
- `GET /download?taskId=x` → `HTTP/1.1 200 OK`
- `GET /websocket` + `Sec-WebSocket-Key` → `HTTP/1.1 101 Switching Protocols`（正确解析到 key）
两条路由都通，首行无丢失。

**教训**：
- **一个协议里"只有一个 port"时，那个端口必须能提供协议约定的全部服务。**
  我按"WS 用 WS 的、HTTP 用 HTTP 的"想当然分了两个端口，但协议只留了一个坑。
- 排查时看到「RX 一条 status 都没有」，就该怀疑**对端根本没走到发 status 那一步** ——
  而它走不到的原因是**我们给它的信息不足以找到下一个服务**。

## P061 · 设备名藏在广播的 service data 里，不在标准设备名里

**现象**：分享卡片里显示的是 **MAC 地址**（`4A:1F:5C:56:FE:B5`），不是「小米15」。

**原因**：huchuan 从头到尾**没读过扫描记录**。
```java
// 原来只有这行 —— 只拿地址
Log.i(TAG, "发现设备: " + d.getAddress() + " rssi=" + result.getRssi());
```
`BluetoothDevice.getName()` 在这里拿不到名字：小米互传的 BLE 广播
**没有标准 Complete Local Name（0x09）**，名字藏在自定义 service data 里。

**CatShare 的做法**（反编译 `ShareActivityKt$deviceScanner$1$1$callback$1`）：

```smali
array-length v10, v3
const/4 v11, 0x6
if-eq v10, v11, :cond_94        # 长度 6 → 只有 MAC
const/16 v6, 0x1b
if-eq v10, v6, :cond_43         # 长度 27(0x1b) → 带名字
...
const/16 v8, 0xa                # 循环起点 = 10
:goto_48
const/16 v5, 0x1a
if-ge v8, v5, :cond_5a          # 循环到 0x19（不含 0x1a）
aget-byte v5, v3, v8
if-eqz v5, :cond_5a             # 遇 0 结束
```
规则：
```
serviceData 长度 == 27 (0x1b)：
    name = ASCII( serviceData[10 .. 25] )   遇 0x00 截断，去掉尾部 "\t"
    id   = "%04x" % ((serviceData[8] << 8) | serviceData[9])
serviceData 长度 == 6：
    只有 MAC，无名字
```

**修法**：
1. `GattClient.parseNameFromScanRecord(ScanRecord)`：按上面规则解名字
2. 扫描回调里解析并缓存（地址 → 名字）
3. `getNameOf(address)` 供上层取用
4. `ShareActivity.onFound`：**广播名字 → 系统设备名 → 地址**，依次回退

**验证**：构造 27 字节 service data（偏移 10 起写 `"Xiaomi 15"`）跑解析逻辑，
得到 `[Xiaomi 15]`；短名 `"Mi9"`+补零 → `[Mi9]`；长度 6 → 正确跳过。

**教训**：
- **`BluetoothDevice.getName()` 拿不到名字 ≠ 没有名字。**
  厂商自定义广播里常常塞了名字，只是不在标准字段里 —— 要读 `getScanRecord()`。
- 之前一直显示 MAC 而"能跑通"，所以这个问题被忽略了很久。
  **能用 ≠ 用对了**：功能链路通了不代表展示层的数据来源正确。

## P062 · 分享卡片的透明背景：主题的 windowBackground 才是元凶

**需求**：「设备框是白色，其他部分是透明的，像悬浮窗」。

**问题**：`setupWindow()` 里已经设置了
```java
w.setBackgroundDrawable(new ColorDrawable(Color.TRANSPARENT));
w.clearFlags(FLAG_DIM_BEHIND);
w.setDimAmount(0f);
```

但整屏仍然被刷成不透明色。**光设 window 的 backgroundDrawable 不够。**

Manifest 里 `android:theme="@style/Theme.HuChuan.Share"`。

另外给卡片加 `card.setElevation(dp(12))`，让它有真正的悬浮阴影。

**验证**（副屏截图逐像素采样，1280×2800）：

## P063 · 关闭接收开关后为什么还能搜到

**现象**：小米15 关了「接收」开关，huchuan 的分享卡片里**仍然列着它**。

**CatShare 的实际行为**（反编译）：

开关的动作在 `StartReceiverActivity.onCreate`：
```smali
const-string v0, "shouldStop"
invoke-virtual {p1, v0, v1}, Landroid/content/Intent;->getBooleanExtra(...)Z
if-eqz p1, :cond_23
    # 关：停 GattServerService
    invoke-virtual {p0, p1}, Landroid/content/Context;->stopService(...)Z
    ...
    # 开：起 GattServerService
    invoke-virtual {p0, p1}, Landroid/content/Context;->startService(...)
```
即开关控制的是 **`GattServerService` 这个前台服务的生死**。

而广播是**服务自己**发的 —— `GattServerService.onCreate()` 里：
```smali
invoke-virtual {p0}, Lmoe/reimu/catshare/services/GattServerService;->startAdv()V
```
`startAdv()` 内部**没有任何 state 判断**，只要服务活着就广播。

**所以**：开关关闭 → `stopService` → 服务销毁 → `stopAdvertisingSet` → **广播停止**。
此时正常应该搜不到。

**那为什么还能搜到？** 两种可能，都需要现场确认：
1. **小米15 那边开关没真正生效**（系统把服务又拉起来了 / 用户点的是别的开关）
2. **我们的扫描缓存**：huchuan 的 `ShareActivity` 里有
   `KnownDevices` 持久化缓存，会把**历史上发现过的设备**直接画进卡片 ——
   那个条目根本不是这次扫描扫到的。

**关键区分方法**：看日志里有没有本次的 `发现设备: XX:XX rssi=...`。
只有 `name=` 解析成功但**没有**本次 `onScanResult` 的条目，就是缓存画的。

**教训**：
- **"列表里有" ≠ "这次扫到了"。** 有本地缓存时，必须先确认条目来源
  （本次扫描 / 历史缓存），否则会把缓存误判成"对端还在广播"。
- 对端状态类的问题，要同时看**我们这边的扫描日志**和**对端的服务状态**，
  不能只凭列表内容下结论。

**P063 修正 —— 真因是缓存，不是对端**

排查后确认：**小米15 关闭接收开关后确实停止了广播**，我们的扫描也确实扫不到。
问题在 huchuan 自己：`ShareActivity.showCached()` 在扫描**之前**就把历史设备
画进卡片，而且**从不移除**。

```java
setContentView(buildCard());
showCached();            // ← 立刻画出上次见到的设备
startScanIfPossible();   // ← 扫描结果只是"补充"，不会删掉旧条目
```

于是：对方关了开关 → 不再广播 → 扫不到 → **但缓存那条一直挂在卡片上**，
用户点下去必然失败（旧版本还会在这里崩溃）。

**修法**：缓存条目降级为"临时占位"，扫描结束必须被证伪。
1. 新增 `confirmed`（本次真正扫到的名字集合）和 `viewOf`（地址 → View）
2. `onFound` 里把名字加进 `confirmed`
3. `stopScan()` 调 `dropUnconfirmed()`：把不在 `confirmed` 里的条目
   从 `byName`/`found`/`addresses` 移除，并从 `listRow` 摘掉对应 View
4. 命中缓存的设备被扫到时，头像从半透明（`alpha=0.55`）点亮为实心

**验证**（真机，构造"缓存里有 Mi 15 但小米15 不广播"）：
```
10:14:40.589 开始扫描 ADV_SERVICE_UUID
10:14:46.603 移除未确认的缓存设备: mi 15      ← 6 秒后正确撤掉
```
反向对照：真机在线时 `onFound` 会写入 `confirmed`，条目保留。

**教训（这次是我自己踩的）**：
- **缓存必须能被证伪。** 只做"加"不做"减"的缓存，会把过期状态当现状。
  凡是"先显示旧的、再异步刷新"的 UI，都要明确回答：
  *刷新失败/没结果时，旧数据怎么办？*
- 这个问题被你一眼看出来，是因为**你按真实语义推理**（关了就不该搜到）；
  而我之前只验证了"能显示设备名"，没验证"不该显示的会不会显示"。
  **负向用例**（不该出现的东西不出现）和正向用例同样重要。

## P064 · 点一次没反应、点两次才成功，且提示「发送到 null」

**现象**：分享 → 点设备头像，第一次提示「正在发送到 **null**」，要再点一次才真的发出去。

**根因**：`ShareActivity.sendTo()` 里
```java
toast("正在发送到 " + found.get(address));
```
`found` 是 `地址 → 名字`。但缓存条目被真实扫描**更新地址**时，
代码只做了 `found.remove(旧地址)` / `found.put(新地址)`，
**`sendTo` 拿到的却是点击那一刻闭包捕获的旧地址** —— `found.get(旧地址)` = `null`。
第一次点击：地址已过期 → `null`；扫描刷新后第二次点击才拿到有效地址。

**修法**：
1. `addDevice()` 里地址迁移时，保证 `found` 的新旧地址映射同步更新
2. `sendTo()` 不再依赖单一来源：`found` → 按地址反查 `byName` → 回落地址本身
```java
String label = found.get(address);
if (label == null) {
    for (Map.Entry<String,String> e : byName.entrySet())
        if (address.equalsIgnoreCase(e.getValue())) { label = e.getKey(); break; }
}
toast("正在发送到 " + (label == null ? address : label));
```

## P065 · 设备列表要实时刷新（对方关开关后应立刻消失）

**需求**：「我在搜到小米15 之后，关闭接收按钮，设备列表应该为空」。

**CatShare 怎么做的**（反编译 `ShareActivityKt`）：
```smali

invoke-virtual {p0, v0, v2, v1}, BluetoothLeScanner;->startScan(...)V
# runPauseOrOnDisposeEffect:
invoke-virtual {v1, p0}, BluetoothLeScanner;->stopScan(ScanCallback;)V
```
回调里**只增不减**：
```smali
:goto_fb
  getId() → areEqual(curId, newId)?
    if-eqz  :cond_113
    move-object v3, v2      # 同一台 → 替换成新的
    move v0, v9
  :cond_113
  ArrayList.add(v3)
...
if-nez v0, :cond_123
  ArrayList.add(v2)         # 没找到 → 追加
:cond_123
  access$deviceScanner$lambda$15(state, list)   # 整体刷新
```

**关键发现**：CatShare **没有超时停止扫描**，扫描在页面存活期间一直开着；
但它**只增不减** —— 所以对方关了接收开关后，
**CatShare 的列表里那条也不会消失**。
（它的"实时"只体现在"新设备立刻出现"，不体现在"离线立刻消失"。）

**我们的做法（比 CatShare 更完整）**：
扫描持续开着 + 给每台设备记 `lastSeen` 时间 + 每 1 秒 sweep 一次，
超过 `STALE_MS`（4 秒）没再收到广播就移出列表。

```java
private static final long STALE_MS = 4000L;   // 多久没广播算离线
private static final long SWEEP_MS = 1000L;   // 检查间隔

private final Runnable sweep = new Runnable() {
    @Override public void run() {
        long now = System.currentTimeMillis();
        for (entry : lastSeen) if (now - entry.value > STALE_MS) dead.add(entry.key);
        for (key : dead) removeByName(key);
        updateHint();
        ui.postDelayed(this, SWEEP_MS);
    }
};
```

**验证**（真机，双向）：
```
10:33:54 发现设备: 59:AA:CB:69:37:B5 name=Mi 15    ← 开关开着，持续广播
10:33:59 设备已离线，移出列表: mi 15               ← 关开关后 5 秒自动消失 ✅
10:34:24 发现设备: 6D:18:97:58:62:84 name=Mi 15    ← 再开开关，立刻回来 ✅
```

## P066 · 缓存按地址去重会堆积重复条目

**现象**：缓存文件里出现 **3 条** `Mi 15`（地址各不相同）。

**根因**：`KnownDevices.remember()` 只按**地址**去重：
```java
for (Entry e : list) if (!e.address.equalsIgnoreCase(address)) next.add(e);
```
但 **BLE 随机地址每次扫描都会变**（实测同一台小米15 先后是
`56:F8:17:…`、`57:15:76:…`、`6F:D2:10:…`、`59:AA:CB:…`、`6D:18:97:…`），
于是每扫一次就新增一条，下次打开卡片重复显示。

**修法**：地址 + **名字**双重去重（名字来自广播 service data，是稳定的）。
```java
if (e.address.equalsIgnoreCase(address)) continue;   // 同地址 → 更新
if (n.isEmpty()) continue;
if (n.equalsIgnoreCase(e.name)) continue;            // 同名字 → 也是同一台
next.add(e);
```

**验证**：清理后重新扫描，缓存从 3 条 `Mi 15` 变为 **1 条**，地址更新为当前广播地址。

**教训**：
- **"唯一标识"要选稳定的那个。** BLE 随机地址天生不稳定，
  拿它当主键必然堆积；名字（或设备端的固定 id）才是正解。
- 这里和 P063 是同一个根源的两面：**缓存的身份判断错了**，
  既导致"旧的不消失"（P063），又导致"同一台被记成多台"（P066）。

## P072 · ★版本协商的 ack 必须带 payload★（接收方的头号拦路虎）

**现象**：小米15 分享过来 → 我们能加入组、能连上 wss、能收到
`versionNegotiation`，然后**对方在约 10 秒后拆组**：
```
P2P-GROUP-REMOVED p2p0 client reason=GO_ENDING_SESSION
```
用户侧表现就是「对方已取消」。

**根因**：我们回的 ack 是 **没有 payload** 的：
```
TX ack:0:versionNegotiation          ← 错，payload 为 null
```

反编译 CatShare `P2pReceiverService$runReceive$2$1$run$1$1`，
它收到 versionNegotiation 后是这样回的：
```smali
const-string v4, "version"
invoke-virtual {v0, v4, v3}, Lorg/json/JSONObject;->optInt(Ljava/lang/String;I)I
invoke-static {v0, v3}, Ljava/lang/Math;->min(II)I        # min(对端version, 1)
invoke-virtual {v5, v4, v0}, Lorg/json/JSONObject;->put(...)   # "version"
const-string v4, "threadLimit"
const/4 v5, 0x5                                            # 5
invoke-virtual {v0, v4, v5}, Lorg/json/JSONObject;->put(...)   # "threadLimit"
```

即：**`{"version": min(peerVersion,1), "threadLimit": 5}`**。
发送方在等这个 payload，等不到就判协商失败、拆组。

**修法**：
```java
int peerVer = (m.payload != null) ? m.payload.optInt("version", 1) : 1;
JSONObject ack = new JSONObject();
ack.put("version", Math.min(peerVer, 1));
ack.put("threadLimit", 5);
c.sendText(new WsMessage("ack", m.id, m.name, ack).toText());
```

**验证**（同一次会话，前后对比）：
```
修之前： TX ack:0:versionNegotiation
         → 10 秒后 P2P-GROUP-REMOVED reason=GO_ENDING_SESSION

修之后： TX ack:0:versionNegotiation?{"version":1,"threadLimit":5}
         RX action:1:sendRequest?{"taskId":"35912","senderName":"Mi 15",
              "fileName":"Screenshot_...jpg","totalSize":605252}   ✅
```
**这是本次最关键的突破** —— 之前所有「连上又取消」都是这个原因。

### 附带发现：CatShare 用 toLowerCase 比较 name
```smali
invoke-virtual {v4, v5}, Ljava/lang/String;->toLowerCase(Ljava/util/Locale;)Ljava/lang/String;
const-string v5, "versionnegotiation"      # 小写
const-string v5, "sendrequest"             # 小写
```
我们用 `equalsIgnoreCase`，语义等价 ✅。

## P074 · p2p0 显示 DOWN 是"正常"的，但没路由就连不上

**不能**直接判定为故障 —— 实测对照组的 CatShare 也经常显示 DOWN。

**真正要看的是路由**：
```
$ ip route get 192.168.49.1
192.168.49.1 via 172.20.0.1 dev wlan0 src 172.20.122.108   ← 走了 wlan0！
```
P2P 组在的时候，`192.168.49.1` 应该走 `p2p0`。
走 `wlan0` 说明 P2P 组已经没了（或还没建好），
于是 TCP 连接从 `172.20.122.108` 发出，永远连不上 GO。

**下载失败的报错正是这个**：
```
java.net.SocketTimeoutException: failed to connect to /192.168.49.1 (port 55733)
  from /172.20.122.108 (port 39812) after 10000ms
```

**另外确认**：CatShare **没有**调用 `bindProcessToNetwork` /
`requestNetwork`（全仓搜过），所以它也是一样依赖系统路由。

**状态**：🟡 `ack` 修复已验证成功；下载环节仍受 P2P 组存活时间影响，待继续。

## P075 · 发送方只给约 9 秒，10 秒窗口等不到用户

## P080 · ★★先下载，再回 status —— 接收成功的关键★★

**这是整个"收不到文件"问题的最终根因。**

**证据链**：
| 请求 | 发出时机 | 结果 |
|---|---|---|
| `/thumbnail` | status **之前** | 每次都 `HTTP 200` ✅ |
| `/download` | status **之后** | 每次都连不上 ❌ |

`/download` 失败时源地址甚至是 `172.20.122.108`（wlan0）——
因为 P2P 组已经拆了，`192.168.49.1` 回落到默认路由。

**日志**（每次都是这个形状）：
```
11:39:23.137  TX action:99:status?{...,"type":1,"reason":"ok"}
11:39:23.142  下载 https://192.168.49.1:57543/download?taskId=19322
11:39:23.150  RX ack:99:status
11:39:23.207  p2p0 interfaceLinkStateChanged: down     ← 仅 65ms 后
```

**根因**：发送方一收到我们的 `status(1,"ok")` 就认为"交接完成"，
约 60ms 后拆 P2P 组（`GO_ENDING_SESSION`）。
我们把 `/download` 放在 status 之后就等于**等对方把网线拔了才去连**。

**修法**：把 `download` 提到 `respond(status)` **之前**：
```java
// 先下载（组还活着，连接能建起来）
boolean ok = downloadOnce(recv, host, info.port, taskId, fileName, clientTls);
// 下载完再回 status（对方据此收尾）
recv.respond(taskId, 99, 1, "ok");
```

**验证（真机，连续成功两笔）**：
```
11:49:56  下载完成 605252 字节 → ...aweme(2).jpg          ✅
11:50:10  下载完成 913530 字节 → ...quark.clouddrive.jpg  ✅
```

**为什么发送方"显示已完成"**：反编译发送方 `/download` 处理器
（`P2pSenderService$runTask$2$httpServer$2$1$2`），它的顺序是
```
Log "Got download request from <addr>"
→ CompletableDeferred.complete()      ← 这一下就判定"成功"
→ 然后才查 taskId，找不到才 "Task ID not found"
```
即**只要有一个 `/download` 请求到达就判成功**，哪怕它随后失败。
所以对方显示"已完成"不代表我们真收到了 —— 别被它误导。

**顺带**：发送方的 `/download` **不检查 status**，只看 taskId，
所以"先下载后 status"不会触发 `Task ID not found`。

## P083 · ★BLE 随机地址导致"第一次发送必然失败"★

**现象**：分享后选设备，**第一次总是发不出去**，第二次就正常。

**根因**：小米15 的 BLE 地址**每次扫描都随机**
（实测 `64:FD:E1:63:C4:EB` / `76:C9:91:F0:89:C6` / `6D:B0:19:04:68:C8` …）。
而 `GattClient.getFound(address)` 是**按地址精确匹配**的：
```java
if (address.equalsIgnoreCase(d.getAddress())) return d;
```
分享卡片上缓存的地址是**上一次扫描**的，永远匹配不上 →
`SenderService` 等满 20 秒后报"未找到设备"。
第二次能成功，是因为第二次列表里已经换成了新扫到的地址。

**修法**：地址匹配不上时，**退化为按名字找**。
名字来自广播 service data，是稳定的。

```java
// GattClient
private final Map<String,String> wantedNames = new ConcurrentHashMap<>();
public void rememberName(String address, String name) { … }

public BluetoothDevice getFound(String address) {
    for (BluetoothDevice d : found.values())
        if (address.equalsIgnoreCase(d.getAddress())) return d;   // 先按地址
    String want = wantedNames.get(address);
    if (want == null) return null;
    for (BluetoothDevice d : found.values()) {                    // 再按名字
        String n = nameOf(d.getAddress());
        if (n != null && want.equalsIgnoreCase(n.trim())) return d;
    }
    return null;
}
```

`ShareActivity` 在三处登记名字：`showCached()`、`onFound()`、`sendTo()`。

**教训**：凡是拿 BLE 地址做长期标识的地方都要小心 —— 这个地址不稳定。

## P084 · 传输成功后被"连接关闭"覆盖成失败

**现象**：明明接收成功、文件已落盘，通知栏却显示「连接关闭」。

## P086 · ★显示设备名而不是 MAC（第一次必现）★

**现象**：第一次发送提示「正在发送到 64:FD:E1:63:C4:EB」，
第二次才显示「正在发送到 Mi 15」。

**根因**（两层）：

1. **`byName` 的 key 是小写的**（`nameKey()` 做了 `toLowerCase`）。
   拿它当显示名会变成 `mi 15`。而 `sendTo` 里恰恰是
   `for (e : byName.entrySet()) label = e.getKey()` —— 取的是小写 key。

2. 更根本的：第一次发送时**地址是缓存里的旧地址**，
   `found.get(address)` 和 `byName` 反查**双双落空** → 回落显示地址。
   第二次时列表已刷新成新地址，才查得到名字。

**修法**：新增一张 `displayName`（地址 → **原始大小写**的名字）专门用于显示：
```java
private final Map<String,String> displayName = new HashMap<>();
```
在 `showCached()` / `addDevice()`（更新分支和新增分支）三处维护。

并且**把名字随 Intent 传给 SenderService**，服务端不用再猜：
```java
i.putExtra(SenderService.EXTRA_TARGET_NAME, nm);
```
`SenderService` 用 `shown` 变量统一显示，拿不到名字才回落地址。

**教训**：**用于比较的 key 不能直接拿去显示**。
凡是 `toLowerCase()` 归一化过的 map，都要另配一张保留原文的表。
这个坑和 P083 是同一类问题的两面 —— 都源于"拿不稳定/被归一化的东西当标识"。

## P087 · ★先扫描，后建组 —— "第一次发送失败"的真正原因★

**现象**：第一次分享必然失败，第二次才成功。

**实测时间线**（原始顺序：步骤 2 建组 → 步骤 4 扫描）：
```
12:20:36  开始建组
12:20:36  TLS 已就绪，统一端口 42289
12:21:12  组就绪 192.168.49.128          ← 建组花了 36 秒
12:21:19  组被系统回收（只活了 7 秒）
12:21:38  才开始扫到 Mi 15               ← 晚了 18 秒
```

**根因**：顺序反了。**建组很快，但扫描很慢**；
而 P2P 组**空转几秒就会被系统回收**（没有客户端连进来）。
于是：组建好了 → 没人连 → 被回收 → 我们才刚扫到设备 → 用已死的组去发。

**关键观察**：`isGroupOwner: false` 和 `p2p0 已就绪` 都出现在
组**被回收之前**，所以日志看上去"一切正常" —— 它确实是正常建立过，
只是**等到要用的时候已经没了**。

**修法**：调换顺序 —— **先扫描锁定目标（慢，且不依赖组），再建组（快）**，
这样组一建好马上就能把 P2pInfo 交付出去。

```java
// 3. BLE 扫描找接收方（★先扫描，后建组★）
client.startScan();
…等扫描到 target…
// 4. ★锁定设备之后再建组★
p2p.createGroup(ssid, psk, true);
// 5. 加密 P2pInfo 并写入 / 交付
```

**验证**：`startScan()` 在 `createGroup()` 之前（源码位置 1882 < 3579）。

**教训**：把"慢的、有依赖的"步骤放在前面，
把"快的、易失的"资源放在**即将被使用**的位置。
P2P 组、蓝牙 GATT 连接这类"空转会被回收"的资源尤其如此 ——
**建好就立刻用，不要让它等**。

### 附带修正：P083 的补充
之前怀疑"第一次失败"是 BLE 随机地址导致 `getFound` 匹配不上。
地址确实是随机的（`77:DD:B3:77:9C:00` 又是一个新值），
按名字兜底仍然必要；
但**主因是这里的顺序问题** —— 即使地址匹配成功，
组也已经不在了。两者都要修。

## P088 · ★rememberName 登记到了另一个 GattClient 实例上★

**现象**：加了按名字兜底（P083）之后，第一次发送**仍然**失败。

**日志**（铁证）：
```
12:31:21.572  正在寻找 77:DD:B3:77:9C:00 …        ← 缓存里的旧地址
12:31:41.718  ❌ 没找到 77:DD:B3:77:9C:00（20 秒超时）
12:32:46.557  发现 74:15:C6:EC:62:D0 name=Mi 15   ← 真实地址，完全不同
```

**根因**：`rememberName` **登记错了对象**。

`ShareActivity.sendTo()` 里调的是它自己那个 `client`：
```java
if (client != null) client.rememberName(address, nm);   // ← ShareActivity 的 client
```
但真正做扫描的是 **`SenderService` 里 new 出来的另一个 `GattClient`**：
```java
// SenderService.send()
client = new GattClient(this, …);     // ← 全新的实例，wantedNames 是空的
```
两个实例各有各的 `wantedNames` map（非静态字段）。
ShareActivity 那个登记完就随 Activity 一起销毁了，
**登记根本没传到扫描器手里** → 兜底逻辑形同虚设 → 第一次必然超时。

**修法**：在 `SenderService` **自己**的 client 上登记：
```java
if (targetAddr != null && targetName != null && !targetName.isEmpty()) {
    client.rememberName(targetAddr, targetName);
}
```

**教训**：**跨组件的内存状态传不过去**。
`ShareActivity` → `SenderService` 之间传的是 `Intent`（进程/生命周期边界），
任何"我在 A 里设好、B 里去读"的假设都必须用 `Intent` extra 显式传递。
这也正是 `displayName`（P086）要用 `EXTRA_TARGET_NAME` 传的原因 ——
同一个道理，我在 P086 已经踩过一次，P088 又踩了一次。

**推广**：凡是"Map/字段在 A 里写、在 B 里读"的跨组件设计，
先问一句：**A 和 B 是同一个对象实例吗？**
不是的话，要么走 Intent/Binder，要么改成静态/单例。

**命名撞车提醒**：`ShareActivity.client` 与 `SenderService.client`
是两个不同的 `GattClient`，名字一样但是两回事 —— 读代码时极易看错。

## P089 · ★onStartCommand 并发：旧任务把新任务的资源关了★

**现象**：第一次分享失败；多次点击后更乱。

**日志**（一次操作里跑了**三个** worker）：
```
12:37:57  第1次：寻找 74:15:C6:EC:62:D0   ← 旧地址，20 秒超时
12:38:11  第2次：寻找 Mi 15               ← 兜底成功，2 秒连上
12:38:11.954  连接状态: 0 status=133      ← GATT 被抢
12:38:21  第3次：寻找 Mi 15               ← 又成功
12:38:22.681  读到设备公钥                 ← 全部走通 ✅
12:38:26.615  对端已连接                   ← 小米15 连上我们 ✅
12:38:26.626  → sendRequest               ✅
12:38:26.631  ← ack:1:sendRequest         ✅
12:38:26.641  ❌ 读取 DeviceInfo 超时（15s）← 第2次线程超时
12:39:26.627  ❌ 等待对方确认超时           ← 因为组被拆了
```

**好消息**：发送协议本身**完全走通**了（协商 → sendRequest → ack 全对）。

**根因**：`onStartCommand` 每次都 new 一个线程并覆盖 `worker` 字段，
**旧线程没人管、继续跑**：

```java
worker = new Thread(...);   // 覆盖，旧线程失联
worker.start();
```

两个后果：

1. **抢 GATT** → `status=133`（两个线程同时连同一台设备）。
2. **更致命**：旧线程超时后走 `finally { cleanup(); }`，
   而 `cleanup()` 关的是**共享字段**：
   ```java
   transfer.close();    // 关掉新任务正在用的服务器
   client.close();      // 关掉新任务正在用的 GATT
   p2p.removeGroup();   // 拆掉新任务刚建好的组！
   ```
   实测第 2 次线程把第 3 次刚建好的组拆了 → 对端等不到确认 → `对方未接受`。

**修法**（两条一起）：

1. **串行化**：新任务先置 `cancelled` 让旧任务主动退出并 `join(3000)`，
   再启动新任务。
2. **只清理自己的资源**：
   ```java
   private void cleanupIfCurrent(Thread self) {
       if (worker != self) { Log.i(TAG, "本轮已不是当前任务，跳过资源清理"); return; }
       cleanup();
   }
   ```
   并在扫描循环、等待确认前加 `if (cancelled) return;` 检查点，
   避免旧任务干等 60 秒拖住新任务。

**教训**：**Service 的 onStartCommand 是可以被重入的**。
只要里面有"长任务 + 共享可变字段"，就必须处理并发 ——
否则不只是浪费，而是**旧任务会破坏新任务的资源**（比单纯失败更危险）。

**推广**：`cleanup()` 这类"关闭所有资源"的方法，
在并发场景下要改成"关闭**我的**资源"。
判断依据：`worker != self`。

## P090 · ★★通知被系统限流，成功提示被丢掉★★

**现象**：发送和接收**都成功了**（文件已落盘、协议全通），
但通知栏**没有任何成功提示**。

**日志（铁证）**：
```
12:44:10.301  E NotificationService: Package enqueue rate is 6.012375.
                Shedding 0|com.huchuan|1001|null|10018. package=com.huchuan
12:44:10.335  W NotificationManager: Shedding notify (update) of
                NotificationKey[...com.huchuan...id=1001], rate limit (5.0) exceeded
12:44:10.393  ✅ 对方已接受          ← 结果算出来了
12:44:10.394  传输结束              ← 但这条通知被 shed 掉了
```

**根因**：**同一包的通知被系统限制在 5 次/秒**（`rate limit (5.0)`）。
我们刷得太快，超限后系统开始 **shed（丢弃）**，
而被丢掉的正好是**最后那条结果通知**。

刷屏的来源有三处：
1. **发送进度**：`Transfer` 里每 64KB 就 `onState("发送中 N%")` → `notify()`
   （829440 字节 ÷ 64KB ≈ 13 次，集中在 ~100ms 内 → 瞬时 13 次/秒）
2. **BLE 扫描回调**：`onFound` 每收到一次广播就 `state("发现 " + addr)`，
   实测每秒 10+ 次
3. **接收端状态**：BLE 读写回调等也可能连续触发

**修法**（三处一起）：

1. **进度节流到 300ms**，且只更新进度条不刷正文：
   ```java
   if (now - lastNotifyMs < 300) return;   // 丢弃中间态
   ```
2. **扫描回调不再刷通知**，只写日志：
   ```java
   public void onFound(...) { Log.i(TAG, "发现设备 " + d.getAddress()); }
   ```
3. **结果通知强制发出**：`lastNotifyMs = 0` 重置节流，
   并且 `✅ / ❌ / 是否接收 / 点通知接受` 这些**关键消息豁免节流**。
4. 结束通知改为 `setOngoing(false) + setAutoCancel(true)`
   —— 传输结束了就不该继续挂着，用户要能划掉。

**教训**：**通知是有配额的（5 次/秒/包）**。
"状态一变就 notify" 这个习惯在**高频回调**（进度、扫描、BLE 读写）场景下
必然触发限流，而且**受害者往往是最后那条最重要的通知**——
因为它恰好出现在频率最高的收尾瞬间。

**推广**：凡是回调可能高频触发的地方，通知都要节流；
并且**关键消息要能插队**（豁免节流）。
节流的实现要注意：不能只判断"距上次多久"，还要给重要消息开后门，
否则"成功"和"失败"这两条会被自己的节流吃掉。

**附带修正**：发送进度原本用 `updateProgressThrottled(pct, 100)` 传百分比，
会被 `human()` 格式化成 `"42 B / 100 B"` —— 语义错乱。
改为显式传百分比 + 单独的 `sendingTotal` 算字节数。

## P091 · 通知白名单：只留用户需要的

用户拍板保留 4 条（原话："2 11 12 30 保留"）：

| 保留 | 内容 |
|---|---|
| 接收 | `已开始广播，等待发送方…` |
| 接收 | `是否接收`（标题 + `✕ 拒绝` / `↓ 接收`）—— **独立通知，不走 state()** |
| 接收 | `✅ 已保存: <路径>` |
| 发送 | `✅ 对方已接受` |

外加所有 `❌` 开头的错误（用户显然需要知道失败原因）。

**做法**：`state()` 前置白名单判断，不在名单里的只写 logcat。

```java
private static boolean isNotifiable(String m) {
    if (m == null) return false;
    if (m.startsWith("✅") || m.startsWith("❌")) return true;  // 结果与错误
    return m.startsWith("已开始广播");
}
```

**被移出通知的（只进日志）**：
接收端 —— 收到连接信息 / 加入组 / 已加入 / 发送方地址 / TLS 就绪 /
已连上发送方 / 正在获取缩略图 / 缩略图已获取 / 已接受 / 已回复接受状态 / 已拒绝
发送端 —— 文件名 / TLS / 统一端口 / 已连接设备 / 读过公钥 / 移除旧组 /
建组 / 组已建立 / p2p0 MAC / P2pInfo / 已交付连接信息 / 传输结束

**顺带修掉两处**：

1. `✅ socket 可用（INTERNET 权限正常）` 是**诊断信息**，
   因为带 `✅` 前缀被白名单放行了（漏网）。改成：通过时只写日志，
   失败时才 `state("❌ socket 不可用: …")`。
2. `对端断开` / `连接关闭` 直接删掉 —— 它们是收尾噪音，
   会紧跟成功通知并覆盖它（P084 加过 `finished` 标志，但不如直接不发）。

**收益不只是干净**：通知有 5 次/秒的配额（P090），
白名单等于**从源头掐掉刷屏**，比只靠节流更稳。

**教训**：**用前缀（`✅`/`❌`）做分类很容易被诊断信息混进来**。
设计白名单时，"结果"和"诊断"要用不同前缀区分，
或者干脆让诊断信息走独立的日志通道。

## P092 · ★stopSelf() 会把成功通知一起撤掉★

**现象**：发送成功、日志明确写了"已发出结束通知"，但通知栏**什么都看不到**。

**日志**（间隔 214ms，这是关键）：
```
13:25:58.226  ZIP 已发送（原始 32761559 字节）   ← 32MB 真的传完了
13:25:58.250  已发出结束通知: ✅ 对方已接受        ← 通知发出去了
13:25:58.464  ForegroundServiceTypeLoggerModule  ← 服务停止
```

**根因**：**前台服务的通知是随服务一起被系统回收的**。

我们的收尾顺序是：
```java
finally {
    cleanupIfCurrent(Thread.currentThread());
    stopSelf();          // ← 撤掉前台服务，连带撤掉它的通知
}
```
而 `finishNotification()` 用的是**同一个 `NOTI_ID = 1001`** ——
它既是前台服务的通知，又是结果通知。
`stopSelf()` 一执行，系统就把这个 id 的通知撤了。
结果通知**只活了 214ms**，肉眼根本看不到。

**修法**：结果通知**必须用独立的 id 和通道**，与服务生命周期解耦：
```java
private static final int NOTI_DONE_ID = 1004;
private static final String CH_DONE = "huchuan_send_done";
…
nm.notify(NOTI_DONE_ID, b.build());   // 不随服务消失
```

**顺带**：接收端**没有**这个问题 ——
它是常驻前台服务（`receive()` 末尾 `while(true) sleep`），从不 `stopSelf()`，
所以通知会一直留着。但这个差异也说明：
**同一个设计在两边的行为不同，是因为生命周期不同**，
不能因为"接收端没问题"就以为发送端也没问题。

**教训**：**前台通知和结果通知不要共用 id**。
前台通知的生命周期绑定在服务上，而"结果"需要在服务结束后继续存在 ——
两者的生命周期不一样，就不该是同一个对象。

**推广**：凡是"服务结束时才产生、但希望服务结束后仍然可见"的东西
（结果通知、toast、写文件），都要确认它**不依附于服务的生命周期**。

## P093 · 接收完成通知的样式（用户指定）

**用户要求**：
```
┌────┬──────────────────────────┐
│ app│ 传输完成                  │   ← 第一行
│图标│ 1个图片 | 来自 Mi 15       │   ← 第二行
└────┴──────────────────────────┘
```

**实现**：
```java
b.setContentTitle("传输完成")
 .setContentText(subtitle)
 .setLargeIcon(Icon.createWithResource(this, R.mipmap.ic_launcher))  // 左侧 app 图标
 .setSmallIcon(android.R.drawable.stat_sys_download)
 .setStyle(new Notification.BigTextStyle().bigText(subtitle));
```

副标题拼装：
```java
private static String buildSubtitle(int fileCount, String mimeType, String senderName) {
    String kind = mimeType.startsWith("image/") ? "图片"
                : mimeType.startsWith("video/") ? "视频" : "文件";
    return Math.max(1, fileCount) + "个" + kind + " | 来自 " + senderName;
}
```
判定顺序：`image/` → 图片，`video/` → 视频，其余 → 文件。
数量用 `Math.max(1, fileCount)` 兜底（对方字段异常时也说得通）。

**踩到的两个技术点**：

1. **左侧图标要用 `setLargeIcon`**，不是 `setSmallIcon`。
   `setSmallIcon` 是状态栏的小图标（必须单色），
   通知卡片**左侧那个大图标**是 `setLargeIcon`。
   资源用 `R.mipmap.ic_launcher`（app 自己的图标，各密度都齐全）。

2. **匿名内部类不能捕获非 final 局部变量**。
   `fileCount`/`mimeType`/`senderName` 是 `joinAndDownload` 的局部变量，
   而 `onDone` 在匿名 `Transfer.Progress` 里 —— 直接引用会编译失败。
   改成用字段传递：`curFileCount` / `curMimeType` / `curSenderName`。

**注意**：Android 通知的"第一行/第二行"就是 `setContentTitle` / `setContentText`，
不是自己画的两行 —— 系统会按主题渲染，展开后由 `BigTextStyle` 接管。
所以**只设置这两个字段**即可，不要试图用换行符模拟两行。

## P094 · 去掉完成通知右上角的图标

**用户要求**：完成通知右侧的图标去掉，只留左侧 app 图标 + 两行文字。

**根因**：那个图标来自 `setSmallIcon(android.R.drawable.stat_sys_download)`。

容易误解的一点：**`setSmallIcon` 不只在状态栏显示** ——
在折叠态通知里，Android 12+ 会把它画到**卡片右上角**。
所以"状态栏图标"这个名字有误导性，它同时承担了两个位置。

**但 `setSmallIcon` 是必填项**，删掉会抛：
```
java.lang.IllegalArgumentException: Invalid notification (no valid small icon)
```

**修法**：完成态换成一个 **1x1 全透明矢量图标**：
```xml
<!-- app/res/drawable/ic_blank.xml -->
<vector android:width="1dp" android:height="1dp"
        android:viewportWidth="1" android:viewportHeight="1">
    <path android:fillColor="#00000000" android:pathData="M0,0 h1 v1 h-1 z" />
</vector>
```
```java
boolean done = doneTitle != null;
b.setSmallIcon(done ? R.drawable.ic_blank          // 完成态：看不见
                    : android.R.drawable.stat_sys_download);  // 传输中：仍有意义
```

**为什么不全去掉**：传输**中**那个下载箭头是有意义的（表示正在进行），
只在**完成态**隐藏。

**验证**：`fillColor="#00000000"`（alpha=00，全透明）；
APK 里 `res/drawable/ic_blank.xml` 存在且 dex 里有引用。

**教训**：Android 通知的"图标"有三个位置，别混：
| API | 位置 |
|---|---|
| `setSmallIcon` | 状态栏 **+ 折叠态卡片右上角** |
| `setLargeIcon` | 卡片左侧大图 |
| `addAction(icon,…)` | 按钮上的图标 |

要"保留左侧、去掉右侧"，就是**留 `setLargeIcon`、把 `setSmallIcon` 换成透明**。

## P095 · ★"右侧的图标"其实是时间戳，不是 smallIcon★

**用户反馈**：把 `setSmallIcon` 换成透明图标后，**右侧的图标还在**。

**说明我 P094 判断错了位置。** 用 `dumpsys notification --noredact`
看完成通知的真实字段，找到了真凶：

```
android.template=String (android.app.Notification$BigTextStyle)  ← ★展开箭头★

icon=Icon(typ=RESOURCE pkg=com.huchuan id=0x7f020000)  ← smallIcon（已换透明）
```

**根因**：通知卡片右侧被画了两样东西：
1. **`when` 时间戳** —— 由 `setShowWhen(true)` 控制（默认就是 true）
2. **`BigTextStyle` 的展开指示** —— `setStyle(new BigTextStyle())` 带来

它们都不是"图标"，但在视觉上就是"右边那一块"。

**修法**（完成态）：
```java
b.setShowWhen(false);        // 不画时间戳
b.setStyle(null);            // 不用 BigTextStyle，消除展开箭头
b.setSubText(null);
b.setProgress(0, 0, false);  // 清掉残留的进度区
```

**验证（真机 dumpsys）**：
```
android.title=String (传输完成)
android.subText=null
android.text=String (1个图片 | 来自 Mi 15)
android.showWhen=Boolean (false)      ← ✅ 已去掉
（无 android.template）                ← ✅ 已去掉
android.largeIcon=Icon (...0x7f030000) ← ✅ 保留
```

**教训**：**用户描述的是"看到的"，不是"代码里的"。**
用户说"右侧的图标"，我直接对号入座到 `setSmallIcon` —— 错了。
正确做法是**先 dump 真实通知字段**，看系统到底放了什么进去。

`dumpsys notification --noredact` 是这类问题的**唯一可靠手段**：
它列出的是**最终渲染的字段**，而不是我"以为设置了什么"。
P094 的教训是"图标有三个位置"，P095 的教训更进一步：
**连"是不是图标"都不该假设 —— 先看 dumpsys。**

## P096 · ★右侧图标 = setLargeIcon（P094/P095 都判断错了）★

**用户反馈链**：
1. "去掉右面的图标" → 我以为改 `setSmallIcon`（P094）→ **无效**
2. 改 `setShowWhen` / `BigTextStyle`（P095）→ **无效**
3. 最终实测：**是 `setLargeIcon`**

**决定性实验**（同一份代码，只改一处，其它全不动）：

| 配置 | 左圆 (1440: 147-217) | 右圆 (1440: 1072-1164) |
|---|---|---|
| 有 `setLargeIcon` | ✓ | **✓** |
| 无 `setLargeIcon` | ✓ | **✗ 消失** |

**结论**：
- **右圆 = `setLargeIcon`** —— PixelOS 把它画在卡片**右侧**，不是左侧
- **左圆 = 系统自动绘制的 app 图标位** —— 移除 largeIcon 后它仍在

**我犯的三个错**（记录以防重犯）：

1. **假设未经验证**：想当然认为 `setLargeIcon` 在左侧、`setSmallIcon` 在右侧。
   Android 文档只保证"largeIcon 用于内容区"，**具体位置由 ROM 布局决定**。
2. **前两次改动都没验证就下结论**：P094 换透明图标、P095 关 showWhen，

3. **浪费了用户的钱**：反复试错 + 大量截图解码。

   而不是连续猜测。

**方法论（这次最终有效的做法）**：
```
1. 明确"要观察的元素"是什么（右圆，1440坐标 x=1072~1164）
2. 只改**一个**候选变量（setLargeIcon）
3. 同条件重测，对比该元素是否还在
4. 结论 = 有因果关系的那个变量
```
**关键**：改完必须**重新测量同一个元素**，
不能像 P094/P095 那样只看"感觉变了没"。

**附带修正**：`ic_blank` 从 1dp 改成 24dp 空画布
（1dp 图标被系统放大到 24dp 槽位时可能渲染成色块，虽非本次主因）。

## P097 · 通知的默认展开/收起

**用户要求**：
- 接收中 / 传输完成通知 → 默认**收起**
- 是否接收（✕拒绝 / ↓接收）→ 默认**展开**

**机制**：Android **没有** `setDefaultExpanded()` 这种 API。
控制展开的是 **`setStyle()`**：

| style | 效果 |
|---|---|
| 不设 / `setStyle(null)` | 固定两行，**不可展开** |
| `setStyle(BigTextStyle)` | **标记为可展开**，展开态显示完整正文 |

**做法**：
```java
// 普通通知（接收中/完成）—— 默认收起
b.setStyle(null);

// 询问通知 —— 默认展开
b.setStyle(new Notification.BigTextStyle()
        .bigText(senderName + " 想发送：" + fileName));
```
询问通知本来就有两个 `addAction`，配合 BigTextStyle，
系统进来就是展开的样子（按钮直接可见）。

**踩到的坑**：我先加了 `b.setStyle(null)`，但**下面还留着**旧的
```java
} else if (doneSubtitle != null) {
    b.setStyle(new Notification.BigTextStyle()...);   // ← 把上面的 null 撤销了
}
```
两条自相矛盾 —— 后面的覆盖前面的。
用 `grep setStyle` 列出**所有**调用点才发现。

**教训**：**同一个 Builder 上对同一属性多次赋值时，后面的会覆盖前面的。**
改动这类"设置型"代码后，要**把所有赋值点列出来核对**，
而不是只看自己刚加的那一行。
（本次 `grep` 一次就暴露了，成本极低 —— 应该早点这么做。）

**另一个事实**：SystemUI 会**记住每个通知的展开状态**。
如果你手动展开过某条通知，之后同类通知可能保持展开 ——
所以验证时要先 `am force-stop` 重发，或点「收起」复位，
否则会误判成"代码没生效"。

## P098 · 设备名改用系统「设备名称」

**用户要求**：对外广播的名字用系统里设的**设备名称**
（设置 → 关于手机 → 设备名称），而不是 `Build.MODEL`。

**实测本机三个来源**：
```
Settings.Global.device_name    = Xiaomi 12 Pro   ← 首选（用户设的）
Settings.Secure.bluetooth_name = Xiaomi 12 Pro   ← 备选（同值）
Build.MODEL                    = 2201122C        ← 原实现，是**代号**
```
代号对方根本认不出是谁 —— 这就是要改的原因。

**实现**：新增 `core/DeviceName.java`，两个 Service 共用
（原来 `SenderService` / `ReceiverService` 各有一份重复的 `deviceName()`，

```java
Settings.Global.getString(cr, "device_name")     // 1
Settings.Secure.getString(cr, "bluetooth_name")  // 2
Build.MODEL                                       // 3 兜底
```
每级都判 `null` 和 `isBlank()`；整段包在 `try/catch` 里 ——

抽到 `core` 包，和其它工具类（BleUtils / RootMacReader）放一起。

**权限**：读 `Settings.Global.device_name` **不需要额外权限**，公开可读。
所以不用申请任何东西。

**注意**：`settings` / `getprop` 在本机被 `engine/bin` 的同名脚本遮蔽
（那些脚本 shebang 指向不存在的 termux 路径），
用绝对路径 `/system/bin/settings`、`/system/bin/getprop` 才正常。

## P099 · ★"寻找一串MAC地址" + 发送失败：过期地址 + 只按地址匹配★

**用户反馈**："为什么总是有寻找一串mac地址的通知，刚刚传文件又失败"

**日志（一次失败的完整证据）**：
```
14:31:57.943  正在寻找 51:19:81:B4:A8:5B …   ← 通知里是 MAC（名字丢了）
14:31:57.945  扫描中…
14:31:58.218  发现设备 6D:A0:3C:EC:76:72     ← ★对方在广播！但它叫另一个地址★
14:31:58.351  发现设备 6D:A0:3C:EC:76:72
   …（每秒一次，连续 20 秒）
14:32:18.080  ❌ 没找到 51:19:81:B4:A8:5B（可能已离开或未开启接收）
```

**关键**：对方**一直在广播**，地址是 `6D:A0:3C:EC:76:72`；
而我们去找 `51:19:81:B4:A8:5B` —— **上一轮扫描的地址**。
小米15 的 BLE 地址每轮都随机变（P083 已记录），所以**必然**对不上。

**两个独立的 bug**：

### bug 1：通知显示 MAC 而不是名字

`addDeviceView` 把地址闭包进了点击回调：
```java
private void addDeviceView(final String addr, ...) {
    avatar.setOnClickListener(... sendTo(addr) ...);   // ← 捕获建 View 时的 addr
}
```
但 `addDevice()` 在扫到真机后会把**旧地址换成新地址**：
```java
addresses.set(idx, addr);  found.remove(oldAddr);  displayName.remove(oldAddr);
```
→ `onClick` 里捕获的还是**旧地址** → `displayName.get(旧地址)` 为 null
→ `EXTRA_TARGET_NAME` 没传 → 通知回落显示 MAC。

### bug 2：只按地址匹配，名字兜底形同虚设

`GattClient.getFound(addr)` 的兜底依赖 `wantedNames.get(addr)`，
但如果地址本身就是过期的，**查不到这条记录**，名字兜底直接 return null。
而且 P088 登记时用的是 `targetAddr` 做 key —— 过期地址 → 查不到。

**修法**（三层）：

1. **点击时重新解析地址**，不用闭包里的旧值：
   ```java
   avatar.setOnClickListener(v -> {
       String live = resolveAddress(name, addr);   // 按名字反查当前地址
       sendTo(live);
   });
   ```
2. **匹配改名字优先**（`GattClient`）：
   ```java
   public BluetoothDevice findByName(String want) { ... }   // 名字直查
   ```
   等待循环里：`名字 → 地址 → lastFound` 依次尝试。
3. **名字三重兜底**：`displayName → found → 反查 byName`，
   任何一层拿到名字，通知就不会显示 MAC。

**验证（用日志里的真实数据模拟）**：
```
目标地址(过期): 51:19:81:B4:A8:5B
目标名字      : Mi 15
实际扫到      : 6D:A0:3C:EC:76:72 (Mi 15)
旧逻辑(地址优先): None                    ← 20 秒后失败
新逻辑(名字优先): 6D:A0:3C:EC:76:72        ← 命中
```

**教训**：
- **动态地址（BLE 随机 MAC）不能作为长期标识**，要用稳定字段（名字）。
  `WifiP2pDevice.deviceAddress` 也有同样问题。
- **闭包捕获的值会过期**：UI 回调里不要直接使用建 View 时捕获的可变数据，
  要么每次重新查，要么捕获不可变的 key。
- 排查这类问题时，**"期望值 vs 实际值"要一起打日志**。
  之前 `onFound` 只打地址，看不出名字解析成功没有；这次加了
  `名字=… 期望名字=…`，一眼就能定位。

## P100 · ★"未识别的设备"：回调时序 + 缓存宽限期★

**用户反馈**："小米15发送页面，检测到该手机是未识别的设备，不显示设备名字，
catshare 是正常的"

### 第一步：先证明"解析到底成功没有"

加了广播原文 dump（**这一步是关键**，否则只能猜）：

```
serviceData uuid=0000ffff-0000-1000-8000-00805f9b34fb len=27
  hex: 00 00 00 00 00 00 00 00 7d 1a 4d 69 20 31 35 00 00 ...
  asc: ........}.Mi 15............
                            ↑ 10~25 = "Mi 15"
  serviceUuids: 00003331-0000-1000-8000-008123456789
  BluetoothDevice.getName() = null
```

**结论：广播格式和我们的解析器都没问题**（`Mi 15` 就在 index 10~14）。
`GattClient` 日志也确认 `名字=Mi 15`。
所以 bug 在**名字怎么传到界面**这一段。

### bug 1：回调时序 —— 构造函数返回前就触发了

```java
client = new GattClient(this, new GattClient.Listener() {
    public void onFound(BluetoothDevice device, int rssi) {
        String parsed = client != null ? client.getNameOf(addr) : null;  // ← client 还是 null!
        String name = parsed != null ? parsed : safeName(device);        // → 回落
    }
});
```

`GattClient` 的扫描回调在 **`new GattClient(...)` 还没返回**时就可能触发，
此时 `ShareActivity.client` 字段仍是 `null` → `getNameOf` 拿不到
→ 回落到 `device.getName()`，而它是 **null**（BLE 随机地址）
→ 界面显示成一串 MAC："未识别的设备"。

**修法**：把名字**随回调直接传出去**，不做反查。
```java
void onFound(BluetoothDevice device, int rssi, String name);   // 新增参数
```

### bug 2：缓存条目被 sweep 秒删（P082 的副作用）

```
14:51:51.568  扫描开始
14:51:52.573  设备已离线，移出列表: mi 15   ← 1 秒就删了
14:51:56.389  才 dump 到设备（广播姗姗来迟）
```

P082 里为了"对方关掉广播后能清掉卡片"，我写了
`lastSeen.put(key, 0L)` —— 但 `0` 意味着**立刻过期**，
`sweep` 每秒跑一次，缓存条目在广播到达前就被删了。

**修法**：改成"当前时间 + 宽限期"：
```java
lastSeen.put(key, System.currentTimeMillis() + CACHE_GRACE_MS);  // 8 秒
```
宽限期内不删（等广播到达），超时仍未确认才删（P082 的诉求也满足）。

### 验证（真机）
```
14:54:58.570  发现设备: 6F:33:FC:C3:C0:26 名字=Mi 15
14:55:00.546  点击设备 name=Mi 15 记录地址=6F:33:FC:C3:C0:26 当前地址=6F:33:FC:C3:C0:26
```
名字正确显示，点击时地址解析也对。

### 教训
1. **"解析失败"和"传丢了"是两回事** —— 先加 dump 证明哪一段坏了，
   再动手改。这次 dump 一次就排除了整个解析器。
2. **构造函数里注册的回调，不要在回调里读"正在构造的那个字段"** ——
   它还没赋值。要么把值随回调传出，要么用两阶段初始化。
3. **P082 的 `lastSeen=0` 是个隐蔽的过度修正**：
   本意是"让缓存能过期"，实际变成"立刻过期"。
   凡是"设成极值来表示状态"的写法都要想清楚**谁会读它、多久读一次**。
4. dump 去重要**按设备**而不是全局 boolean —— 原来只 dump 第一台，
   结果 dump 到的不是目标设备（6F:33 vs 52:B7），关键信息漏掉了。

## P101 · 对方列表里显示"未知的设备"：我们没广播名字

**用户反馈**："我是说在小米15的列表里，小米12pro这个机子没名字，显示未知的设备"

**根因**：我们的广播**只发了 UUID，没发名字**：

```java
AdvertiseData data = new AdvertiseData.Builder()
        .addServiceUuid(new ParcelUuid(BleUtils.ADV_SERVICE_UUID))
        .setIncludeDeviceName(false)     // ← 只在自己这头解析，没告诉别人
        .build();
advertiser.startAdvertising(settings, data, advertiseCallback);
```

我们**解析**对方广播的代码是完整的，但**自己广播**时什么都不带 ——
所以小米15 扫到我们只知道"有个设备在广播"，拿不到名字 → "未知的设备"。

**catShare 的做法**（`GattServerService.startAdv`）：
名字放在 **scan response**，不是主广播包：
```kotlin
val scanRespData = AdvertiseData.Builder().apply {
    val data = ByteArray(27)
    System.arraycopy(ByteArray(8), 0, data, 0, 8)      // [0..7] 0
    System.arraycopy(BleUtils.RANDOM_DATA, 0, data, 8, 2)  // [8..9] senderId
    // [10..25] 名字（UTF-8，超 15 字节按字符边界截断 + '\t'）
    data[26] = 1
    addServiceData(ParcelUuid.fromString("0000ffff-0000-1000-8000-00805f9b34fb"), data)
}.build()
advertiser.startAdvertisingSet(params, advData, scanRespData, ...)   // ★带 scan response★
```

注意布局和我们**解析**时的偏移完全对应（P083 记的 `name = data[10..25]`）——
原来只做了一半（能读不会写）。

**修法**：
1. 新增 `buildScanResponse()`，按 27 字节布局填名字
2. 改用 **`startAdvertisingSet`**（`startAdvertising` 不支持 scan response）
3. `stop()` 里要 `stopAdvertisingSet(advSetCallback)` ——
   注意这个 API 收的是 **callback**，不是 set 句柄（踩过）

**UTF-8 截断**要小心：直接按字节切会切出半个汉字。
catShare 的做法是逐字符回退直到成为原串前缀，然后补 `'\t'`
（对方解析时看到 `\t` 就知道名字被截短了）。

**验证**：
```
15:04:33.951  BLE 广播已启动（含扫描响应：名字=Xiaomi 12 Pro）
15:04:33.977  广播集已启动 status=0 txPower=-10
```

**教训**：**协议的"读"和"写"要用同一份布局定义。**
我们 P083 花了很大力气搞清"名字在 serviceData[10..25]"，但那只是**解析**；
广播时却完全没写。以后实现这类协议，读写两侧应共用常量/构造函数。

## P102 · 名字只显示尾巴 "Pro"：主广播包缺「品牌/5GHz」条目

**用户反馈**："现在对方显示本机的名字只有 'Pro'"

（上一轮 P101 加了扫描响应里的名字，广播也报 `status=0` 成功，
但对方只拿到 `Pro` —— `"Xiaomi 12 Pro"` 的**最后 3 个字符**。）

### 排查：先确认两边布局真的一样

```
我们的 27 字节：00×8 | 7d 1a | "Xiaomi 12 Pro" | 00 00 00 | 01
                d[0..7]  d[8..9]   d[10..22]      d[23..25] d[26]
```
- 名字只有 13 字节（< 15），**根本没走截断分支**
- 写入起点 `d[10]`、`arraycopy` 长度，与 catShare **逐字一致**
- 所以**扫描响应本身是对的** —— 问题不在我们写的那 27 字节

### 真因：主广播包少了一个条目

对照 catShare 的 `startAdv()`：

```kotlin
val advData = AdvertiseData.Builder().apply {
    addServiceUuid(ParcelUuid(BleUtils.ADV_SERVICE_UUID))
    addServiceData(                                    // ★我们没有这个★
        ParcelUuid.fromString("000001ff-0000-1000-8000-00805f9b34fb"),
        Arrays.copyOfRange(BleUtils.RANDOM_DATA, 0, 6)
    )
}.build()
```

我们之前只发了 UUID（P101 之前连名字都没有，P101 加了扫描响应），
**主广播包里始终缺这个 6 字节条目**。

### 这个条目是什么

**内容没人读**，信息全编码在**条目的 UUID** 里：

```
UUID = 000001ff-0000-1000-8000-00805f9b34fb
对方 ByteBuffer(16) 拆 msb = 0x000001ff_00001000
  arr[2] == 0x01 → supports5Ghz = true
  arr[3] == 0xff → brandId（未知品牌）
```

注意 `000001ff-...` 是 **16-bit UUID**（前 8 位 000001ff + 标准基址），
编码时压缩成 2 字节，所以主广播包才放得下：
`addServiceUuid(18) + addServiceData(1+1+2+6=10) = 28 ≤ 31` ✅

### 为什么缺了它名字就丢

小米15 的内置「互传」把这个条目当作**"这是一台合格互传设备"的标志**。
没有它 → 不认这台设备 → **不去读扫描响应** →
只能退回系统蓝牙名（`Xiaomi 12 Pro` 在某些路径下被截成 `Pro`）。

**修法**：主广播包补上该条目
```java
.addServiceData(ParcelUuid.fromString("000001ff-0000-1000-8000-00805f9b34fb"),
                BleUtils.brandData())          // 6 字节，内容随意（补零）
```

### 验证
```
15:12:22.394  BLE 广播已启动（含扫描响应：名字=Xiaomi 12 Pro）
15:12:22.425  广播集已启动 status=0 txPower=-10
```

### 教训
**"我按协议填对了字段" ≠ "对方会来读这个字段"。**
广播是一个**多包结构**（主广播包 + 扫描响应），
对方往往要先在主包里看到"资格标志"，才会去读扫描响应。
抄协议时不能只抄**数据布局**，还要抄**完整的包结构** ——
P101 我只补了扫描响应，漏了主包里的条目，于是又绕了一轮。

**排查手法**：当"格式明明一样却不对"时，逐字段对比**写入侧**的完整构造过程，
不要只比对自己关心的那一小段。这次一对照 `startAdv()` 就看出少了一整行。

## 关于「把小米互传移植到本机」

**结论：不做，也不建议做。** 难度不是"大"，是**方向不对**。

### 证据一：16 个特权权限，装机必须**系统签名**

```
BLUETOOTH_PRIVILEGED      LOCAL_MAC_ADDRESS        ACCESS_SURFACE_FLINGER
INTERNAL_SYSTEM_WINDOW    MANAGE_USERS             INTERACT_ACROSS_USERS
NETWORK_SETTINGS          OVERRIDE_WIFI_CONFIG     TETHER_PRIVILEGED
WRITE_SECURE_SETTINGS     START_TASKS_FROM_RECENTS STOP_APP_SWITCHES
STATUS_BAR                EXPAND_STATUS_BAR        READ_FRAME_BUFFER
GET_TASKS
```

这些是 `signature|privileged` 级别。PixelOS 上没有小米的平台签名证书，
**装上去也申请不到**。改包名没用（权限名对不上）；
自己签平台证书没用（ROM 不认）。

### 证据二：9 个小米私有权限 —— 这些"权限"在 PixelOS 上**根本不存在**

```
com.miui.mishare.PERMISSION.ALL          com.miui.mishare.PERMISSION.NFC
com.miui.onehop.permission.MIRROR        com.xiaomi.mirror.permission.MIRROR_DEVICE_CHANGED
com.xiaomi.permission.BIND_CONTINUITY_SERVICE
com.miui.securitycenter.permission.SYSTEM_PERMISSION_DECLARE
com.miui.zman.permission.SECURITY_SHARE
com.miui.bugreport.permission.DUMP_CACHED_LOG
com.miui.mishare.permission.GUIDE
```

`AndroidManifest` 里声明一个**未定义**的权限，安装时会被**静默丢弃**，
代码里 `checkPermission` 永远返回 denied → 功能直接不可用。
（不是"可能有问题"，是确定不工作。）

### 证据三：两个 native 库依赖小米框架

```
lib/arm64-v8a/libmicontinuity_sdk.so   2,070,104 字节   ← com.xiaomi.*
lib/arm64-v8a/libmiexpress-jni.so      2,141,672 字节   ← miui.*
```
`libmiexpress-jni.so` 里能看到 `miui` 符号，说明它要调 MIUI 框架的服务。
PixelOS 上没有这些服务，JNI 调用会失败。

### 证据四：包体差 146 倍

```
小米互传 4.12.0:  12,809,233 字节 (12.2 MB)
我们的 huchuan:       87,502 字节 (85 KB)
```

那 12 MB 里绝大部分是**小米生态耦合**（NFC 一碰传、妙享桌面 mirror、
Continuity SDK、bugreport 集成、CTA 合规……），
真正"互传协议"那部分，**我们已经自己实现完了**。

### 证据五：协议核心我们已经有了

在小米互传的 dex 里能搜到：
```
✅ 00003331-0000-1000-8000-008123456789   ADV_SERVICE_UUID
✅ websocket / /download / /thumbnail       WS + HTTP 路由
✅ versionNegotiation / sendRequest / threadLimit   协议消息
✅ P2pInfo
❌ catShare                                （那是 CatShare 加的字段）
```
这些我们在 huchuan 里**已经全部实现并验证过**（能收能发，实测 32MB 传输成功）。

### 那"移植"具体难在哪

不是改改包名的问题，因为要改的是：

| 要替换的东西 | 工作量 |
|---|---|
| 16 个特权权限 → 用公开 API 重写等价功能 | 大（部分**无等价 API**，如 `LOCAL_MAC_ADDRESS`） |
| 9 个私有权限 → 找到对应服务的替代品 | **不可能**（服务本身不存在） |
| 2 个 native 库 → 反编译或重写 | 极大 |
| MIUI 框架调用（NFC/妙享/Continuity）→ 全部砍掉 | 中 |
| 系统签名需求 → 无解 | **不可能** |

**本质上这不是"移植"，是"照着重写一遍"** —— 而重写的结果，
就是我们现在的 huchuan。

### 建议

你现在两条路：

1. **继续用 huchuan**（推荐）：协议层已经打通，剩下的是 UI/体验打磨。
   需要什么功能就加什么，比移植可控得多。
2. **真要"小米互传的完整功能"**（妙享桌面、NFC 一碰传、跨端流转）：
   那依赖 MIUI 框架，**只能刷回 MIUI**，没有第三条路。

**如果你想要的是某个具体功能**（比如"一碰传"或"电脑端互传"），
告诉我具体是哪个 —— 有些能用公开 API 实现，有些确实不行，
我可以说清楚哪个能哪个不能。

## P104 · ★参考小米互传：整包广播布局 + 设备类别★

## P105 · ★"版本协商超时"盖掉成功通知：共享 boolean + join 超时★

**现象**：用户连发三次，通知里出现"发送失败 / 版本协商超时"，
但实际有一次是**成功**的。

**日志（两条线索对照，一眼看出问题）**：

| 线程 | 开始 | 过程 | 结果 |
|---|---|---|---|
| 4221 | 15:28:46.913 | 建组 DIRECT-dpkePfSo → 等待对方接入 | 15:29:48 **版本协商超时** |
| 4265 | 15:28:55.773 | 建组 DIRECT-l0ITqMsz → 对端已连接 | 15:29:02 **传输完成** ✅ |

```
15:28:46.913 4221 开始发送（建组 DIRECT-dpkePfSo）
15:28:48.048 4221 等待对方接入…          ← 对方还没连上
15:28:55.773 4265 开始第二次发送          ← 用户又点了一次
15:28:56.154 4265 移除旧组…              ← ★把 4221 的组拆了★
15:28:59.835 4265 对端已连接 → 成功
15:29:48.059 4221 版本协商超时            ← ★失败通知盖掉成功★
```

**根因**：串行化写成了「共享 boolean + join(3s) 后重置」：

```java
cancelled = true;
oldWorker.join(3000);     // 只等 3 秒
cancelled = false;        // ★不管旧线程死没死都把标志清了★
```

旧线程**正卡在 60 秒的等待里**，3 秒根本等不到它退出；
标志被清掉后它"复活"，60 秒后跑完 finally 发出失败通知。

**而且**：全文件只有 2 处 `cancelled` 检查，都在**扫描等待循环**里 ——
真正阻塞 60 秒的 `transfer.requestSend(...)` 后面那处检查
在调用**之前**，进了等待就没法取消了。

**修法：代次（generation）取代共享 boolean**

```java
final long myGen = ++generation;      // 每次新任务 +1
...
if (!isCurrent(gen)) return;          // 取代是**单向、不可逆**的
```

- `isCurrent(gen)` = `gen == generation`，旧任务永远无法"复活"
- `join(2000)` 后即使旧线程还活着也**不等了** —— 靠代次让它自己作废
- ★监听器所有回调都加代次守卫★：`onState` / `onResult` 先查 `isCurrent(gen)`，
  被取代的那轮连通知都不碰（这才是真正止血的地方）
- `state(m, gen)` 重载：作废的那轮只写日志，不更新通知

**为什么代次比 boolean 可靠**：
boolean 是**可变共享状态**，谁都能把它设回去；
代次是**单调递增的令牌**，一个任务要么是当前代、要么永远不是。

**教训**：
1. **"取消标志"不能用 join(timeout) 之后无条件重置** ——
   join 超时 ≠ 线程已退出。要么确认退出，要么用不可逆的令牌。
2. **取消检查要放在真正阻塞的地方**。只在循环里查、把阻塞调用放后面，
   等于没查。正确做法是让**阻塞调用本身可中断**，或在回调层拦截。
3. **通知类的副作用要在"最后一道关口"再校验一次身份**（这里是 listener 回调），
   而不是只依赖调用点前面的检查 —— 异步世界里状态随时会变。

## P106 · ★广播 UUID 写死了：对方认不出我们★

（在 P101/P102 之后，小米15 仍显示"未知的设备"）

**关键突破：把抓到的 62 字节拆成两个 31 字节包**

BLE 单包上限 31 字节，而抓到 62 字节 → 必然是
**主广播(31) + 扫描响应(31)** 拼起来的。拆开后才看清：

```
主广播   02 01 02 | 11 07 8967452381...3133 0000 | 09 16 1e1b 7d1a00000000
         flags    | Complete 128-bit UUID        | ServiceData UUID16=0x1b1e, 6 字节

扫描响应 1e16 ff ff | 00*8 7d1a "Mi 15" ... 01
         ServiceData UUID16=0xffff, 27 字节     ← 名字在这条
```

**★两条 serviceData 的 UUID 不同★** —— 这是之前一直没看出来的：
- 主广播：`0x1b1e`
- 扫描响应：`0xffff`

**我们错在哪**：
| | 主广播 UUID | 扫描响应 UUID |
|---|---|---|
| 原来 | `0x01ff` ❌ | `0xffff` ✅ |
| 实测小米15 | `0x1b1e` | `0xffff` |

主广播的 UUID 是**动态算出来的**（反编译 `v1/c.e`）：
```java
private static ParcelUuid c(byte hi, byte lo) {
    return ParcelUuid.fromString(
        String.format("0000%02x%02x-0000-1000-8000-00805f9b34fb", hi, lo));
}
// v1/c.e: addServiceData(c(z1.a.j(), v1.c.h(ctx)), copyOfRange(x1.f(),0,6))
```
`h(ctx)` 是能力位域（bit0=5GHz, bit2/bit3/bit4 各种能力）。

**修法**：
- `BleUtils.serviceDataUuid(hi, lo)` 按同样规则拼 UUID
- `DeviceProfile.manufactureHi()=0x1b`、`flagsLo()=0x1e`（照实测值）
- 主广播用动态 UUID；**扫描响应保持 `0xffff`**

**★走过的弯路（要记住）★**：
我一开始以为两条同 UUID，就把扫描响应也改成动态的 —— **改错了**。
拆成两个 31 字节包之后才发现两条本来就不同。
**"先按 31 字节边界拆包"应该是第一步**，而不是盯着 62 字节整体猜偏移。

**验证**：
```
15:40:14.391 主广播 serviceData UUID = 00001b1e-0000-1000-8000-00805f9b34fb
15:40:14.393 BLE 广播已启动（含扫描响应：名字=Xiaomi 12 Pro）
15:40:14.408 广播集已启动 status=0 txPower=-10
```
两条 UUID 现已与小米15 实测值一致。

## P107 · ★"小米15 搜不到设备"：GATT 特性属性不对称 + 主广播 UUID 冒用★

### 症状与真因（两个独立问题）

**① 我上一步改错了主广播 UUID（我造成的）**

P106 我按"小米15 实测主广播 UUID16=0x1b1e"把它从 `0x01ff` 改成动态的 `0x1b1e`，
**结果小米15 直接搜不到我们了**。

那个 `0x1b1e` 里的 `0x1b` 来自小米私有的 `z1.a.j()`，
是**小米内部编码**。非小米设备冒用它，对方会在扫描阶段就过滤掉。

→ **改回 `0x01ff`**（互传联盟/CatShare 的公开约定值）。

对照实验（同一台设备、只改这一个变量）：
| 主广播 UUID | 结果 |
|---|---|
| `0x01ff` | ✅ 能搜到 |
| `0x1b1e` | ❌ 搜不到 |

**② GATT 特性属性不对称（真正的"搜到但用不了"）**

改回 UUID 后日志显示：小米15 **能连上**我们，但连上后什么也不做：

```
15:43:30.809  GattServer: 连接状态: 49:7D:D3:E2:E0:FF → 2    (连上了)
15:43:40.173  GattServer: 连接状态: 49:7D:D3:E2:E0:FF → 0    (10 秒后自己断开)
   ↑ 中间**没有任何读请求**
```

**根因**：我们的两个特性属性不对称：

| | props | perms |
|---|---|---|
| 我们 CHAR_STATUS | `READ` | `READ` |
| 我们 CHAR_P2P | `WRITE` | `WRITE` |
| **catShare 两个都是** | `10` = READ\|WRITE | `17` = READ\|READ_ENCRYPTED_MITM |

CatShare 的代码：
```kotlin
svc.addCharacteristic(BluetoothGattCharacteristic(CHAR_STATUS_UUID, 10, 17))
svc.addCharacteristic(BluetoothGattCharacteristic(CHAR_P2P_UUID,    10, 17))
```
**两个特性用同一组值**，都同时可读可写。

对方连上后在**找一个能读的属性**，我们的 STATUS 虽然可读、
但对方可能按 UUID 顺序试到了 P2P（只写）→ 拿到
`GATT_READ_NOT_PERMITTED(0x02)` → 放弃 → 10 秒后断开。

**修法**：
1. 两个特性都用 `PROPERTY_READ | PROPERTY_WRITE` + `PERMISSION_READ | PERMISSION_WRITE`
2. `onCharacteristicReadRequest` **两个 UUID 都接受**
   （原来只认 CHAR_STATUS，读 CHAR_P2P 直接返回 not permitted）
3. 加日志：`读请求 uuid=… offset=…` / `localDeviceBytes 还没准备好`

**验证（真机，小米15 主动发送）**：
```
15:46:09.541  已连上发送方，等待传输请求…
15:46:09.739  来自 Mi 15 的文件: Screenshot_...jpg (918077 字节, 1 个)
15:46:11.870  ✅ 已保存: /storage/emulated/0/Download/互传/Screenshot_...(3).jpg
```
✅ 完整握手 + 接收成功，且**发送方名字正确解析出 "Mi 15"**。

### 教训
1. **不要冒用对方的私有值。** `0x1b1e` 看着是"实测值"，
   但它是小米**内部**编码，抄过来等于自称小米设备 —— 直接被过滤。
   该抄的是**公开约定**（`0x01ff`），不是"对方私有实例的当前值"。
2. **"能连接" ≠ "能用"。** 小米15 连上又断开，
   如果不看**中间有没有读请求**，很容易误判成"网络问题"。
   日志要能回答"连上之后对方做了什么"。
3. **抄协议要把构造细节抄全。** 我看着 catShare 的
   `BluetoothGattCharacteristic(uuid, 10, 17)` 却按"语义"写成了
   只读/只写 —— 而**数字 10/17 本身就是协议的一部分**。

静音三连 + 不显示角标，与小米互传逐条对应。

#### ③ 通知 ID 编排（`g3/r`）

★**这个设计最值得学**★ —— 小米互传不是写死 ID，而是**按 taskId 动态分配**：

```java
private final HashMap<String,Integer> f = new HashMap<>();  // taskId → 通知ID
private int g = 0x7e3;                                      // 起始 ID

// g3/r.f() 分配
int id = this.g;
this.g = id + 1;
this.f.put(task.taskId, Integer.valueOf(id));

// g3/r.c() 使用：先查，查到就复用同一 ID
Integer id = f.get(taskId);
if (id == null) return;
nm.notify(id.intValue(), builder.build());
```

**为什么比写死 ID 好**：
1. **同任务原地更新** —— 进度 10%→90% 用同一 ID，系统是"更新"
   而非"再插一条"，**不闪烁、不堆积**
2. **多任务并存** —— 两个任务两个 ID，互不覆盖
   （我们原来写死 `NOTI_ID=1002`，第二次传输会**盖掉**第一次的通知）

我们实现 `NotiIds.of(taskId)`，起始 ID 用 `0x7e3`（照抄）。

✅ 4 条渠道，ask 会响、其余静音
✅ `mSound=null / mVibrationEnabled=false / mShowBadge=false` 与小米互传一致

另加了通知日志，以后核对不用每次 dumpsys：

### 教训
1. **评估要先查"对方用了什么 API"，而不是猜复杂度。**
   我原本以为复刻小米通知 = 做 RemoteViews 定制卡片（大工程），
   实际它 `setStyle` 都是 0 处，全是标准 API。**先查再估，能避免误判。**

   小米互传把传输渠道设成 HIGH 但静音 —— 高重要性只为置顶。
   很多人会把 HIGH 和"响铃"绑死，结果进度通知疯狂响。
3. **通知 ID 应该是"任务身份"的映射，不是写死的常量。**
   写死 ID 在多任务场景下必然互相覆盖。


```
applyState switchOn=true mode=1  ← 生效时却变成了 1（10分钟）
```

**修法**：加 `programmaticSwitch` 守卫

```java
programmaticSwitch = true;
mainSwitch.setChecked(switchOn);
programmaticSwitch = false;

// 监听器
if (programmaticSwitch) return;   // 程序化改动，mode 已定好，别覆盖
```

**教训**：**程序化改 View 的状态前，先想想它的监听器会不会反噬。**
`setChecked/setSelection/setText` 这类都可能触发回调，
"先设数据再设 View"的顺序很容易被回调改回去。

## P112 · ★去掉设备缓存 —— 学小米互传的"纯事件驱动"发现★

### 用户的判断（先说结论：用户是对的）

用户："小米15没开接收开关，但是本机小米12pro在相册分享，设备列表已经显示了
小米15了…我觉得这是不对的，说明列表不是实时的，而是提前缓存的，会误导用户，
产品有问题"

我第一版还替这个设计辩护（"缓存占位 vs 确认在线，设计如此"）—— **那是从实现
角度看问题**。从用户角度看：一个显示"当前可发送设备"的列表里混进了**7 天前**
的历史记录，而且那些条目**照样可点**，点了白等 20 秒才报"没找到"。这就是误导。

### 证据

`KnownDevices.java`：
```java
private static final long TTL_MS = 7L * 24 * 60 * 60 * 1000;   // ★7 天★
```

实测缓存内容：
```xml
<string name="devices">77:73:DC:13:44:34&#1;Mi 15&#1;1792140479142</string>
```

`ShareActivity.onCreate` 顺序：
```java
showCached();          // ← 先把 7 天内的历史设备全摆出来
startScanIfPossible(); // ← 才开始扫描
```

还有 `avatar.setAlpha(fresh ? 1f : 0.55f)` —— 用**半透明**表示"这是缓存"。
但**用户根本看不懂 0.55 是什么意思**，所以"设备变亮了"看起来就像
"它刚刚出现在附近"，实际可能只是扫描确认了一个 7 天前见过的设备。

### ★小米互传怎么做的（用户让我去学）★

反编译 `IDiscoveryCallback.aidl` —— 接口只有三个方法：

```java
public abstract void onDeviceChanged(RemoteDevice);
public abstract void onDeviceLost(String deviceId);   // ★显式的"设备走了"★
public abstract void onDiscoverFailure(int);
```

`i2/f.onDeviceLost()` 的核心实现就一句：

```java
this.g.remove(deviceInfo.getDeviceId());   // ★直接移除，不是"标记过期"★
```

**关键结论**：
- 小米互传**没有任何设备缓存** —— 没有 TTL、没有 SharedPreferences
- 列表里有 ⟺ **现在真的在广播**（纯事件驱动）
- 设备离开是 `onDeviceLost` **事件**，不是 4 秒 polling 超时

对比表：

| | 小米互传 | 我们（改之前） |
|---|---|---|
| 列表来源 | 只有本轮发现 | **7 天缓存 + 本轮** |
| 移除方式 | `onDeviceLost` 事件 → 立即 `remove` | polling 超时 |
| 状态标识 | `DeviceStatus.state`（IDLE/BUSY）+ `busyReason` | alpha 0.55（看不懂） |
| 设备名 | `RemoteDevice.KEY_NICKNAME` | 已实现 ✅ |

**附带发现**：`DeviceStatus` 有 `BUSY=1` / `BUSY_REASON_AP=2` /
`BUSY_REASON_MIRROR=1` —— 小米互传会**明确告诉用户"这台设备忙"**，
而不是让用户点了干等。这个以后可以借鉴。

### 改法

```java
// onCreate
searching();            // 显示"正在搜索附近设备…"
startScanIfPossible();  // 不再 showCached()

// showCached() → searching()
private void searching() {
    if (hint != null) hint.setText("正在搜索附近设备…");
}
```

`KnownDevices.remember()` **保留** —— 它记的是"见过的设备"，
以后可以做"最近发送过"之类的功能，只是**不再拿它填充列表**。

**代价**：打开后有 2~4 秒空窗（BLE 扫描要时间）。
**但这是诚实的**：空窗 + "正在搜索…" 比 "假设备 + 点不动" 好得多。
catShare 也是这个行为。

1. **"秒出"如果是靠假数据实现的，那就是产品缺陷**，不是体验优化

## P113 · 扫描节奏：两档模式 + 超时 4s → 2s

**用户问**："几秒扫一次"

### 先纠正一个概念：BLE 扫描**不是**"几秒扫一次"

我们用的是**连续扫描**：

```java
scanner.startScan(filter, settings, scanCallback);   // 一直开着，不重启
```

设备一发广播就回调，**发现是毫秒级的**，没有"轮询间隔"这回事。

真正带"秒"的只有**移除**：

| 参数 | 改前 | 改后 | 作用 |
|---|---|---|---|
| `STALE_MS` | 4000 | **2000** | 多久没收到广播 → 判定离开 |
| `SWEEP_MS` | 1000 | 1000 | 每秒巡检一次 |

### ★小米互传的两档扫描模式（反编译发现）★

`com/miui/mishare/connectivity/ble/central/a.smali` 里出现了**两个** ScanMode：

```smali
const/4 v3, 0x2   →  setScanMode(2)   // SCAN_MODE_LOW_LATENCY（活跃）
const/4 v2, 0x0   →  setScanMode(0)   // SCAN_MODE_LOW_POWER （省电）
```

它在两档之间切换。我们照做：

```java
// ShareActivity
onResume() → client.setScanMode(SCAN_MODE_LOW_LATENCY);  // 前台，不漏包
onPause()  → client.setScanMode(SCAN_MODE_LOW_POWER);    // 后台，省电
```

**注意**：`ScanSettings` 是 `startScan` 的参数，**系统不支持运行时调档** ——
所以 `GattClient.setScanMode()` 内部必须 **stop + start** 重启扫描。
方法做成**幂等**（值没变直接 return），避免 onResume 反复调用时无谓重启。

**不能停扫**：切后台只降档、不停扫。否则用户切回来时列表是空的，
又要重新等 2~4 秒。

### 为什么 STALE_MS 选 2 秒

- 小米互传靠 `onDeviceLost` **事件**移除（协议层通知），比拿秒表数快得多
- 我们没有那个事件，只能轮询 —— 那就把窗口压短
- **不能更短**：小米互传广播间隔约 300ms~1s（连发若干包），
  2 秒 = 至少跨 2 个广播周期，偶发丢一两个包不会误踢；
  1 秒在信号弱时会看到设备"闪烁"
- **不能再长**：4 秒的空白窗口用户能明显感觉到"它走了还挂在上面"

## P114/P115 · ★「开关关着，小米15却扫描到本机」—— 三个缺陷★

**用户**："本机没开接收开关，小米15却扫描到了本机"

先说结论：**用户是对的，而且不是一个 bug，是三个叠在一起。**

---

### 缺陷一（最直接）· `advSet` 从未赋值 → 广播根本停不下来 → P115

`GattServer.stop()` 里：

```java
if (advSet != null && advertiser != null) advertiser.stopAdvertisingSet(advSetCallback);
```

而 `advSet` 字段**声明了、读了，却从来没有被赋过值**：

```
210:    private android.bluetooth.le.AdvertisingSet advSet;      // 声明
272:        advertiser.startAdvertisingSet(..., advSetCallback); // 启动（没接返回值）
305:        if (advSet != null && ...) stopAdvertisingSet(...);   // 读
```

⇒ `advSet` 恒为 `null` ⇒ 那个 `if` **永远不成立** ⇒
`stopAdvertisingSet()` **一次都没被调用过**。

而它上面那句 `advertiser.stopAdvertising(advertiseCallback)` 对
`startAdvertisingSet` 启的广播**无效** —— 那是 legacy API 的停止方法。

**结果**：关掉接收开关后，GATT Server 确实注销了，但 **BLE 广播一直在发**，
对方设备仍然能扫描到本机。这正是用户报的现象。

#### 怎么发现的（关键判据）

`dumpsys bluetooth_manager` 里，广播记录如果**还在广播**，显示的是：

```
└Start time   : 10-16 17:22:32.180
└Elapsed time : 49087ms              ← ★没有 Stop time★
```

而正常停止后是：

```
└Start time   : 10-16 17:24:27.048
└Stop time    : 10-16 17:24:46.087   ← ★有 Stop time★
```

**`Elapsed time` ↔ `Stop time` 就是"还在广播 / 已停止"的判据。**

同时对照服务侧日志：服务已退出（`ServiceRecord: 0`）、
`GATT Server Map: Entries: 0`（服务端注销了），
但**日志里从来不出现 `onAdvertisingSetStopped` 的「广播集已停止」** ——
这三条一起就把问题锁死在"广播集没停"上。

#### 修法

1. `onAdvertisingSetStarted(set, ...)` 里 **`advSet = set;`**（把句柄存下来）
2. `stop()` 里 **去掉 `advSet != null` 前置条件** ——
   `stopAdvertisingSet` 收的本来就是 **callback**，不需要句柄
3. 顺带记录：这个 `android.jar` 里 `AdvertisingSet` **没有 `close()`**
   （javap 验证，隐藏 API）；补调 `enableAdvertising(false,0,0)` 只会让
   蓝牙栈报 `BtGatt.AdvertiseManager: enableAdvertisingSet(): Bad advertiserId=0`，
   纯属污染日志，所以最终没留。

**实测修复后**：

```
17:27:33.312  GattServer: 广播集已启动 status=0 set=true
17:27:51.355  Receiver:   定时到点 → 自动关闭接收并停止服务
17:27:51.375  GattServer: GATT server 已停止
17:27:51.385  GattServer: 广播集已停止     ← ★这个回调以前从不出现★
dumpsys: Start 17:27:33.304 → Stop 17:27:51.371   ← ★有 Stop time★
```

### 缺陷二 · `onStartCommand` 会**自动把开关打开** → P114

```java
// 进了服务就说明开关是开的（磁贴/设置页负责置位）
if (!ReceiverState.isRunning()) {
    ReceiverState.enable(this, DEFAULT_TTL_MS, false);
}
```

这个注释里的假设是**错的**。而且 `ReceiverState` 原来是
**纯内存 static**（`running`/`deadline`/`permanent` 全是 `static volatile`，
**完全没有持久化**）—— 进程一死（Thanox 杀、装更新、内存回收）就全部归零。

于是：服务被重新拉起时内存态是 `false` ⇒ **自动打开开关 + 开始广播**。

**实测证据**（开关是关的，直接 `am start-service`）：

```
17:15:10.607  HuChuan.RecvState: 接收开关打开，定时 10 分钟
dumpsys:  [000001ff-…, 6] 正在广播          ← 我们的品牌数据 + 服务 UUID
```

#### 修法

1. **给 `ReceiverState` 加持久化**（`huchuan_receiver_state`：
   `running`/`permanent`/`deadline`），新增 `restore(ctx)`；
   `enable`/`disable` 都落盘。
   *注意*：`activeTransfers`/`pausedRemaining` **不持久化** ——
   传输不可能跨进程存活，存了只会制造假状态。
2. `onStartCommand` 里 `restore(this)` 之后：
   - 没开 → `stopForeground(REMOVE)` + `stopSelf()`，**绝不广播**
   - 已过期 → `disable()` + 同上
3. `restore()` **只在服务里调用**。若让 UI 也调，会出现
   "磁贴显示开着、其实没服务在广播"的假象。

这样两个方向都对：
- 进程被杀后服务重启（`onDestroy` 没跑，盘上还是 `running=true`）→ 继续广播、保留倒计时
- 用户明确关掉（`onDestroy` 跑过，盘上 `running=false`）→ 重启也不广播

---

### 缺陷三 · 超时只由磁贴执行 → 面板一收就没人管 → P114

`ReceiverState.enforceExpiry()` **全项目只有一个调用点**：
`ReceiverTile.tick`。而那个 tick：

```java
onStartListening() → ui.postDelayed(tick, 1000L);   // 面板打开才开始
onStopListening()  → ui.removeCallbacks(tick);      // ★面板收走就移除★
```

而 `ReceiverService.receive()` 原来是：

```java
while (!Thread.currentThread().isInterrupted()) Thread.sleep(1000);   // 没有任何超时判断
```

⇒ **快捷面板不打开，10 分钟超时永远不会执行，服务会一直广播。**
（实测一条广播记录 16:43:40 → 16:55:58 = **12 分 18 秒**，超过约定的 10 分钟。）

#### 修法

把超时判断搬进服务自己的循环，与面板开不开无关：

```java
while (!Thread.currentThread().isInterrupted()) {
    if (ReceiverState.enforceExpiry(this)) {
        Log.i(TAG, "定时到点 → 自动关闭接收并停止服务");
        break;
    }
    Thread.sleep(1000);
}
stopForeground(STOP_FOREGROUND_REMOVE);
stopSelf();
```

### 测试夹具的坑（下次直接用）

## P117 · ★通知误报「❌ java.lang.InterruptedException」★

**用户**："通知提示❌java.lang.interruptedexception,什么情况"

### 结论：不是错误，是**正常收尾**被判成了失败

用户点磁贴把接收**关掉**，收尾时弹了个 ❌ 通知，看起来像传输失败。

### 完整时间线（17:36:25）

```
17:36:25.405  Tile: onClick，当前=true              ← 用户点磁贴关闭
17:36:25.405  RecvState: 接收开关关闭
17:36:25.425  GattServer: GATT server 已停止         ← onDestroy 收尾
17:36:25.425  Receiver: 接收失败                      ← ★误报★
17:36:25.425  Receiver: java.lang.InterruptedException
                at java.lang.Thread.sleep(Native Method)
                at com.huchuan.ReceiverService.receive(ReceiverService.java:164)
17:36:25.428  通知[1002] 正文=❌ java.lang.InterruptedException
```

### 机理

`ReceiverService.onDestroy()` 里有：

```java
if (worker != null) worker.interrupt();      // ← 关服务时打断工作线程
```

而工作线程正卡在 P114 我加的保活循环里：

```java
while (!Thread.currentThread().isInterrupted()) {
    if (ReceiverState.enforceExpiry(this)) { ... break; }
    Thread.sleep(1000);        // ← 第 164 行，interrupt() 让它抛异常
}
```

异常冒到外层被 `catch (Throwable)` 接住：

```java
try { receive(); }
catch (Throwable t) { Log.e(TAG, "接收失败", t); state("❌ " + t); }   // ← 打成"接收失败"
```

**但没有任何东西失败** —— 用户主动关开关，打断线程是**预期行为**。

**这是我 P114 改动引入的**：加了 `enforceExpiry` 后，"超时自动关"也会走
`stopSelf() → onDestroy() → worker.interrupt()`，撞上的概率大增，
所以用户比以前更容易看到。

### 修法（两处，两层保险）

1. **循环里就地捕获** —— 能走到 sleep 就说明本来就该收尾，直接 `break` 不 rethrow：
   ```java
   try { Thread.sleep(1000); }
   catch (InterruptedException ie) {
       Log.i(TAG, "收尾中断（正常）→ 退出保活循环");
       break;
   }
   ```
2. **外层单独 catch `InterruptedException`**（`catch (Throwable)` 之前），
   只记 info 日志，**不打 ❌、不弹通知**。

`SenderService` 也一并改了 —— 同样有 `catch (Throwable) → state("❌ " + t)`，
虽然它的 worker 目前不会被 `interrupt()`（用代次令牌而不是打断），
但 `send()` 阻塞在网络 I/O 上时仍可能被打断，属于同类隐患。

### 验证（副屏，走用户报的那条路径）

**关开关路径**（原来报错的地方）：
```
17:40:39.879  接收开关关闭
17:40:39.897  GATT server 已停止
17:40:39.898  收尾中断（正常）→ 退出保活循环     ← ★原来是 ❌ InterruptedException★
17:40:39.898  接收服务收工，停止广播
17:40:39.910  广播集已停止
```

**超时路径**：
```
17:41:11.369  接收开关关闭
17:41:11.372  定时到点 → 自动关闭接收并停止服务
17:41:11.394  广播集已停止
```

```
InterruptedException / 接收失败 次数: 0     ← 全清
```

### 教训

**"线程被打断"和"操作失败"是两回事。** `Thread.sleep`/`wait`/`join`
抛 `InterruptedException` 是 Java 的**协作式取消协议** ——
调用方 `interrupt()` 是在说"该收工了"，不是"出错了"。

凡是用 `catch (Throwable)` 把一切都打成错误的地方，都要**
先单独放行 `InterruptedException`**。这个坑在**任何**有工作线程 + 收尾
`interrupt()` 的服务里都会重复出现。

### 先查证："收到图片"是不是我们的 bug —— **不是**

找到用户那次接收的实际文件：

```
  181579 字节   uid=10214  17:39
```

uid 10214 是 `com.android.providers.media.module`（系统媒体库），
**不是我们（10018）** —— 这文件是浏览器/媒体库侧导出的。

文件头验证是**真 JPEG**：

```
0000000 377 330 377 340 \0 020 J F I F \0 001 001
        └─ FF D8 FF E0 ─┘ └── "JFIF" ──┘
```

所以小米浏览器分享网页时，**它自己导出的就是一张图片**（分享卡片截图），
`EXTRA_STREAM` 指向那个 jpg。

### 但确实有我们的问题：`EXTRA_TEXT` 从来没读过

```java
private Uri extractUri(Intent intent) {
    if (Intent.ACTION_SEND.equals(action)) {
        return intent.getParcelableExtra(Intent.EXTRA_STREAM);   // 只读 STREAM
    }
    ...
}
```

全项目 `grep EXTRA_TEXT` **零命中**。于是：

| 浏览器发的 | 我们原来的行为 |
|---|---|
| 只有 `EXTRA_STREAM`（图片） | ✅ 收下图片 |
| 只有 `EXTRA_TEXT`（网址） | ❌ `pendingUri == null` → toast"没有可发送的文件"→ 直接退出 |
| 两者都有 | ⚠️ 只发图片，**网址被丢掉** |

用户要求："没 STREAM 就把文字/网址当文件发"。

### 修法：写成 .txt 文件，走同一条发送链路

**为什么不给发送流程加"文字专用通道"**：
发送链路（BLE 广播 → P2P → WS → ZIP）**只认文件**，
为文字单开一条路要改协议两端，成本和风险都大。
而写成 `.txt` 后**接收端零改动**就能收到，网址还是完整原文。

```java
private Uri uriFromSharedText(Intent intent) {
    CharSequence cs = intent.getCharSequenceExtra(Intent.EXTRA_TEXT);
    if (cs == null || cs.toString().trim().isEmpty()) return null;
    // 文件名必须带 .txt —— 否则对方打开是未知文件，

    ...写 UTF-8（含 EXTRA_SUBJECT 作为首行标题）...
    return Uri.fromFile(out);
}
```

```java
pendingUri = extractUri(intent);                       // 先找文件流

```

## P120 · ★分享网址发出去是 0 字节 —— 我自己 P118 引入的恶性 bug★

**用户**："本机往外分享网址也不对，是个txt，但是为空"

### 证据（协议报文里就写着 0）

```json
TX action:1:sendRequest?{
  "fileName":"分享内容_1792144402730.txt",
  "mimeType":"text/plain",
  "fileCount":1,
  "totalSize":0                ← ★0 字节★
}
```

本地文件确认：

```
-rw------- 0 字节  cache/分享内容_1792144402730.txt
```

而 ShareActivity 的日志明明说"已写成"：

```
17:53:22.731  HuChuan.Share: 分享的是文字/网址（27 字），已写成 分享内容_1792144402730.txt
```

**写入成功、发送时变 0 字节** —— 问题出在中间的 `copyToCache`。

### 根因：`copyToCache` 把源文件自己截断了

P118 我给 `copyToCache` 加了一段"从 `file://` 路径取文件名"的兜底：

```java
if (name.startsWith("share_") && "file".equals(uri.getScheme())) {
    ... name = 从 uri.getPath() 取文件名 ...      // → "分享内容_XX.txt"
}
File out = new File(getCacheDir(), name);          // ★和源文件同名同目录★
InputStream in = getContentResolver().openInputStream(uri);
FileOutputStream fos = new FileOutputStream(out);  // ★先把文件截断成 0★
while ((n = in.read(buf)) > 0) fos.write(...);     // ★读的是刚被清空的自己★
```

时序：

1. `uriFromSharedText()` 写 `cache/分享内容_XX.txt`（27 字节）✅
2. `sendTo()` → `copyToCache(uri)`
3. 我新加的兜底把 `name` 解析成 **`分享内容_XX.txt`**（跟源文件一模一样）
4. `out` 指向**同一个路径**
5. `new FileOutputStream(out)` **截断为 0 字节**
6. `openInputStream` 读的是**已被清空的同一个文件** → 恒定 0 字节

**P118 之前不会有这个问题**，因为那时 `name` 总是回落到
`share_<13位时间戳>`，跟 `分享内容_<ts>.txt` 不同名，复制是"自己→别人"。
**我为了修"后缀丢失"引入了"自我覆盖"。**

### 修法：同名就不复制

```java
try {
    if ("file".equals(uri.getScheme())
            && out.getCanonicalPath().equals(new File(uri.getPath()).getCanonicalPath())) {
        Log.i(TAG, "分享内容已在缓存中，直接使用: " + out.getName());
        return out;      // 它本来就是要发送的那个文件，不需要复制
    }
} catch (Throwable ignored) { }
```

用 `getCanonicalPath()`（解析 `..`、软链）而不是字符串比较，
`file://` 的 path 可能有编码差异。

### 验证（副屏，真发给 Mi 15）

```
修前： sendRequest totalSize=0
修后： TX action:1:sendRequest?{"fileName":"分享内容_1792144526415.txt",
                              "mimeType":"text\/plain","totalSize":48}
      本地文件仍是 48 字节（没被截断）

文件内容：
  测试标题

  https://www.xiaomi.com/test?id=99
```

### 教训（两条，都很贵）

1. **"修一个 bug 引入另一个 bug"最典型的形态：改名/改路径**
   —— 任何"把 A 复制到 B"的逻辑，只要 B 可能等于 A，
   就必须**先判断是不是同一个文件**。`FileOutputStream` 会无条件截断。
2. **`catch (Throwable ignored) { }` 吞异常掩盖了症状**
   —— `copyToCache` 里那个 query 抛异常被吞，我看不到；
   真正该做的是把这类"兜底"路径也记一条日志。
   这次是因为链路太短（写文件→发送），直接从 `totalSize` 一眼看出来。

3. **验证要端到端**。P118 我只测到"文件写出成功"就收工了，
   没走 `copyToCache`（因为附近没设备，没点发送）。
   **"写出成功" ≠ "发送正确"** —— 中间还有一次复制。

### ★我们照抄时遇到的唯一障碍：没有 androidx★

小米互传用 `androidx.core.content.FileProvider`，但**我们这套构建
只对着 `android.jar` 编译**（`build.sh` 里 `-cp "$CPJAR"`，没有 androidx 依赖）。

**解法**：自己写一个**纯 framework API** 的最小 ContentProvider
（`app/src/com/huchuan/FileContentProvider.java`），行为对齐：

| FileProvider | 我们的实现 |
|---|---|
| `getUriForFile(ctx, auth, file)` | `FileContentProvider.uriFor(file)` |
| `openFile` → fd | ✅ `ParcelFileDescriptor.open(f, MODE_READ_ONLY)` |
| `query` → `DISPLAY_NAME`/`SIZE` | ✅ `MatrixCursor` |
| `getType` → MIME | ✅ `MimeTypeMap` 按扩展名 |

manifest：
```xml
<provider
    android:name=".FileContentProvider"
    android:authorities="com.huchuan.fileprovider"
    android:exported="false"
    android:grantUriPermissions="true" />
```

`exported="false"` + `grantUriPermissions="true"` —— 跟 FileProvider 一致：
默认谁都读不到，只有我们显式授权（`FLAG_GRANT_READ_URI_PERMISSION`）的组件能读。

### 实现要点

1. **记住落盘路径**：`onDone(ok, msg)` 里从 `"✅ 已保存: /path"` 剥出路径，
   并且**校验文件真的存在**才记（`stripSavedPath`）。
2. **只在该挂的时候挂**：只有 `done && lastSavedPath != null` 才
   `setContentIntent`。传输中/失败时点击没有意义，不设 intent
   （系统默认行为就是"点一下收起来"）。
3. **`FLAG_IMMUTABLE` 必填**（targetSdk 35）：API 31+ 不传 flag 会抛
   `IllegalArgumentException`。
4. **`setAutoCancel(true)`**：打开文件后通知自动收起，不挡地方。

## P122 · ★落盘路径别解析字符串 —— 按「目录 + 文件名」反推★

**用户**："默认路径不就是 `/storage/emulated/0/Download/互传/` 这里吗，你根据文件名来反推"

### 问题
P121 里 `lastSavedPath` 是从 `onDone(ok, msg)` 的**回调文案**里剥出来的
（`stripSavedPath`：从 `"✅ 已保存: /path"` 抠路径）。这条路的毛病：

- `Transfer` 的回调文案**格式变过**（早期是裸路径，后来带前缀）→ 解析是脆的
- 一旦格式再变，抠不出来 → `lastSavedPath = null` → 通知不挂
  `contentIntent` → **用户点击没反应**，且不报错、很难发现

### 修法（`ReceiverService.resolveSavedFile()`）
我们自己知道两件事，直接拼就行，不依赖任何回调字符串：

```
保存目录 = recvDir()      →  /sdcard/Download/互传/
文件名   = curFileName    →  sendRequest 里带的 fileName
```

`onDone` 里改成**优先反推、解析文案只做兜底**：

```java
String p = resolveSavedFile();          // ★主路径
if (p == null) p = stripSavedPath(msg); // 兜底
lastSavedPath = p;
```

### ★★重名的坑（第一版写错了）★★
用户要求"不覆盖"，所以第二次收同名文件会存成 `name(1).jpg`。
于是"**精确名存在就返回**"是**错的** —— 它命中的是**上一次的旧文件**：

```
18:06 收到 → Screenshot_xxx.jpg        （旧）
18:17 再收到 → Screenshot_xxx(1).jpg   （新，本次的）
精确名查询返回 18:06 那个  ← 点通知打开的是旧文件
```

**正确做法**：把 `name` 和 `name(N).ext` **全部收集起来，取 mtime 最新**的
—— 本次刚落盘的一定最新。

### 实测验证（拿真实文件跑算法，非推理）
`/storage/emulated/0/Download/互传/` 里正好有一组三连同名文件：

| 文件 | mtime |
|---|---|
| `…quark.clouddrive.jpg` | 19:00:36 |
| `…quark.clouddrive(1).jpg` | 19:17:40 |
| `…quark.clouddrive(2).jpg` | **19:20:58** ← 最新 |

```
算法选中   : …clouddrive(2).jpg   ✅
应选       : …clouddrive(2).jpg
旧做法选中 : …clouddrive.jpg      ← 旧文件（bug 复现）
```

### 附带修的小问题
`openFileIntent()` 原来用 `getContentResolver().getType(uri)` 取 MIME —— 走一次
跨进程 provider 查询，在**通知构建路径**上不划算，且 provider 未就绪时返回
`null` 会退化成 `*/*`。改为直接用 `sendRequest` 里带的 MIME（`curMimeType`）。

### 教训
**能从自己掌握的事实推出来的，就不要去解析别人的输出格式。**
"解析回调字符串"看起来省事，但它把正确性绑在了别人的文案格式上 ——
而文案是最容易变、最难测的东西。

### 二、真因：10 分钟空闲自动关（设计行为）

dumpsys 里本机广播的**完整起停时间线**：

```
18:54:19 → 19:04:21    (10分02秒)   ← 到期自动关
19:15:52 → 19:24:10    ( 8分18秒)   ← 手动关
19:24:45 → 19:34:48    (10分03秒)   ← ★到期自动关
          ★ 19:34:48 → 19:44:15 完全没广播，空窗 9分27秒 ★
19:44:15 → 19:44:34    (   19秒)    ← 用户点磁贴开了又关
19:44:37 → 19:46:25    ( 1分48秒)
19:46:31 → 19:56:34    (10分03秒)   ← ★再次到期自动关（本次当场抓到）
19:56:52 → (活动)                    ← 用户又开；期间 19:56:01 成功收到 Mi 15 的文件
```

**"每个窗口都正好 10 分钟"这个规律，是本次排查当场抓到的**：

```
dumpsys:  Start time 19:46:31.436 → Stop time 19:56:34.948
          AppRecord(19:46:31 ~ 19:56:34, reason=REASON_UNREGISTER_SERVER)
日志:     19:56:34 前后 → GATT server 已停止 / 广播集已停止
          19:56:52 用户再开 → 恢复接收状态: running=true deadline=1792152412239
```

10分03秒后**广播真的停了** —— 这不是推理，是实时观测到的。
所以"搜不到"是可复现的：**开一次 → 10 分钟后必然搜不到，除非重新开或改成「永久」。**

**用户"搜不到"的时段正好落在那 9 分 27 秒的空窗里** —— 此时本机确实一个广播都没发，
小米15 当然搜不到。而空窗的起因就是上一段刚好满 10 分钟到期。

日志同时排除了"是不是 bug 提前退"：
```
19:44:15.515 Tile: onClick，当前=false   → 开
19:44:34.600 Tile: onClick，当前=true    → 关   ← 这 19 秒是用户自己关的
19:44:35.182 Tile: onClick 忽略（防抖 582ms）
19:44:37.163 Tile: onClick，当前=false   → 再开
```

### 三、为什么这个设计特别容易让人误判

1. **磁贴/通知没有任何"还剩多久"的可见提示** —— 用户不知道它自己关了，
   表现就是"刚才还能用，现在搜不到了"，很像 bug。
2. **自动关是用户自己当初要求的**（"开一次必须等满 10 分钟"），所以这是**行为符合约定**，
   不是实现错误。真正缺的是**可见性**。

### 四、解决 / 缓解

- **要一直能被搜到** → 长按磁贴进设置页，把「10 分钟」改成 **「永久」**
  （`ReceiverState.PERMANENT_TTL_MS`，入口 `TileSettingsActivity`）。
- 排查时先看这两个数（5 秒判断，别重读协议）：
  ```sh
  dumpsys bluetooth_manager | sed -n '/GATT Advertiser Map/,0' | head -40   # 有没有 Stop time
  cat /data/user/0/com.huchuan/shared_prefs/huchuan_receiver_state.xml      # running / deadline
  ```

## P125 · ★推送历史：三个连环坑（分叉 / 压平 / 参数当分支名）★

### 背景
本地积压 **13 改 + 39 未跟踪**，最后 commit 停在 `26e0961`。
整理成 6 个提交后要推送，结果接连踩到三个坑。

### 坑 1：老推送脚本会**压平历史**

`scripts/api-push.mjs` 的做法是：
```js
const files = git('ls-files');            // 当前工作区全部文件
... 建一棵 tree ...
const msg = git('log', '-1', '--pretty=%B');  // 只取**最后一条** message
POST /git/commits { message: msg, tree, parents: [远端head] }
```
→ **本地 6 个提交推上去只剩 1 个。**
后果已经发生了：远端那 9 个提交 vs 本地 22 个，**零个共同 SHA**。

### 坑 2：历史分叉 → `Invalid revision range`

修好脚本后按"逐条重放"写，用了 `${remoteHead}..HEAD`，直接报：
```
fatal: Invalid revision range 0b2374ea9a2cb06cefa3a44f47b1c9a083e28452..HEAD
```
因为那个 `remoteHead` 是老脚本重写出来的，本地根本没有这个对象。

**判定分叉的正确做法**：
```sh
git cat-file -e <remoteHead>^{commit}   # 本地有 → 正常差集；没有 → 分叉
```

**分叉时能不能覆盖？先证明内容等价，而不是凭感觉。**
本次用逐字节比对坐实了"两边最新树其实一样"：
```
远端 0b2374e 文件数 41   本地 559ebb6 文件数 41
仅远端有 0   仅本地有 0   共有文件 SHA 一致 41/41
```
> ⚠️ 比对时**必须**给 git 加 `-c core.quotepath=false`，否则中文文件名被输出成
> `"docs/\350\270\251..."`，而 GitHub API 返回的是解码后的 UTF-8 —— 两边看起来
> 完全不重合，会得出"内容不同"的**错误结论**（本次先踩了一次，7 个文件全被误报）。

所以脚本改成：**默认拒绝**分叉覆盖并打印旧 head 作回滚锚点，要显式 `--force-history`。

### 坑 3：`--force-history` 被当成了**分支名**

```js
const BRANCH = process.argv[2] || 'main';   // ← 错
```
跑 `node scripts/api-push-history.mjs --force-history` 时 `argv[2]` 正是这个开关，
于是：
```
更新 refs/heads/--force-history → 9c7db1d
```
**23 个提交全建好了，却推到了一个叫 `--force-history` 的新分支上，`main` 纹丝不动。**
（好消息：脚本"最后才动分支"的设计让数据没丢，提交对象都在，直接复用即可。）

修法：**过滤掉所有 `-` 开头的参数**，剩下的第一个才是分支名：
```js
const positional = process.argv.slice(2).filter(a => !a.startsWith('-'));
const BRANCH = positional[0] || 'main';
```
并加了 `--head=<sha>` 快速修分支（先 `GET /git/commits/<sha>` 确认存在再 PATCH）。

### 性能坑：没有去重 → 请求数 ×8 → 卡死

第一版逐提交逐文件上传，实测跑了几百次往返还没到一半，**直接卡死**。
量化后发现：
```
提交数 23
累积条目 = 986        ← 脚本实际发的 POST 次数
去重后 blob = 124     ← 真实需要的上传量（1.27 MB）
```
即**同一个文件在多个提交里被反复上传了几十次**。
改成：先扫全历史收集 blob sha **去重**，一次性并发（8 路）上传，建树时查缓存
→ 请求数 **986 → 124（-87%）**，一轮跑完。

### 最终结果
```
远端 main = 9c7db1d，23 个提交（M1 → P125 完整演进）
远端 69 文件 vs 本地 69 文件：仅远端 0 / 仅本地 0 / 内容不同 0
★★ 逐字节完全一致 ★★
```

### 教训
1. **推送脚本要保留历史**，别用"当前工作区建一棵树"的写法 —— 那不是提交，是快照。
2. **中文路径比对必须 `core.quotepath=false`**，否则会得到完全相反的结论。
3. **`argv[2]` 拿位置参数是危险的**，选项一多就会把开关当数据；务必先过滤 `-` 前缀。
4. **GitHub 的 blob 是内容寻址的**，跨提交复用同一份内容；不做去重就是白白多发几倍请求。
5. 推送前**先算清请求量**（累积条目 vs 去重后），几百次往返在这个网络环境必然卡死。
