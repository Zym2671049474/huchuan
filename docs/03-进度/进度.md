## 发送失败根因：P2pInfo.mac 填了假地址（P058）

### 现象
选中小米15 → "正在发送到 Mi 15" → 无反应。日志：`❌ 版本协商超时`。

### 定位（靠 catShare 对照实验）
用户确认 **catShare 同一时刻还能正常传给小米15** → 排除环境问题，是 huchuan 协议实现有偏差。
逐字段对比 catShare 的 smali 后发现 `P2pInfo.mac` 的取值完全不同：

| | 值 |
|---|---|
| catShare | `getMacAddressByName("p2p0")`（真实） |
| huchuan | `"02:00:00:00:00:00"`（写死假值） |

**小米15 会拿这个 mac 回连**，假地址导致它连不上 → `AP-STA-DISCONNECTED` → WS 服务端从未收到连接。

### 修复
- `P2pManager.Session` 加 `interfaceMac`
- `P2pManager.readInterfaceMac()`：`NetworkInterface.getHardwareAddress()` → 回落 sysfs
- `SenderService` / `GattServer` 都改用真实 MAC（拿不到则记日志，不编假值）

### 实测
- 本机 `p2p0` MAC = `66:dd:e9:a7:fb:17`（与控制台 `ip link` 一致）
- 构建通过、装机成功

## 传输链路打通 ✅（P060）+ 设备名修复（P061）

### 单端口修复（P060）—— 决定性突破
之前「小米15 点了接受却提示对方已取消」的真因：
**WS 和 HTTP 起了两个端口，但 P2pInfo 只带一个 port。**

小米15 拿这个 port 连上 WS 后，要用**同一个 port** 做 `GET /download` ——
打到 WS 服务上，连不上，于是它显示「已取消」。

CatShare 用 Ktor `embeddedServer` **单端口挂两个路由**，所以没这个问题。

改为 `Transfer.startUnifiedServer()`：一个端口，先窥探请求行分流
（`/websocket` → WS 握手，其它 → 文件下载）。

**实测成功日志**：
```
→ WS 握手: GET /websocket HTTP/1.1
← ack:0:versionNegotiation
→ sendRequest {...}
← ack:1:sendRequest
→ 文件下载: GET /download?taskId=1792115188530 HTTP/1.1
```

## 分享卡片的三处修复（P064 / P065 / P066）

### P064 · 点两次才成功、提示「发送到 null」
根因：`sendTo` 用 `found.get(address)` 取名字，而缓存地址被扫描更新后，
闭包捕获的**旧地址**在 `found` 里已经不存在 → `null`。
修法：取名字改成三级回落（found → 反查 byName → 地址本身），
并在 `addDevice` 的地址迁移分支里同步维护 `found`。

### P065 · 实时刷新（对方关开关后条目应消失）
参考了 CatShare 的实现（`LifecycleResumeEffect` + 只增不减的列表），
发现**它其实也做不到"离线即消失"** —— 只增不减，关了开关条目仍在。

我们做得更完整：扫描持续开着 + 每台设备记 `lastSeen` +
每 1 秒 sweep、超 4 秒未广播即移除。

实测双向验证：
```
10:33:54  发现设备 … name=Mi 15      ← 开关开着
10:33:59  设备已离线，移出列表: mi 15  ← 关开关 5 秒后消失 ✅
10:34:24  发现设备 … name=Mi 15      ← 再开开关立刻回来 ✅
```

### P066 · 缓存堆积重复条目
根因：`KnownDevices.remember` 只按地址去重，而 BLE 随机地址每次都变
（实测同一台机器出现过 5 个不同地址），导致缓存里堆了 3 条 `Mi 15`。
修法：地址 + 名字双重去重。实测从 3 条降为 1 条。
